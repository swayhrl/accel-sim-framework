# 一、逐项审查目前关于 L2 的判断

论文目标架构中，L1 是 SM 私有的，L2 由全 GPU 共享并划分为多个分区，每个分区连接内存控制器，原子操作也由 L2 分区内的原子单元处理；论文还假设 L1 采用写穿透，而 L2 采用写分配、写回策略。这个基本出发点是成立的。

但从这些事实到“L2 一定更容易出现组相联瓶颈”“WBUF 一定很小”“统一池一定有高收益”，中间还缺少量化证据。

## 1. “L2 服务更多 SM，因此更容易发生组相联瓶颈”

**部分成立，但不能这样直接写进论文。**

更准确地说，一个 Set 是否容易被瞬态请求占满，取决于：

[
P_{\text{set-pressure}}
\sim
\frac{\lambda_{\text{set}}\times E[T_{\text{non-replaceable}}]}{A}
]

其中：

- (\lambda_{\text{set}})：到达该 Set 的事务速率；
- (T_{\text{non-replaceable}})：一条 Way 因 Fill、Writeback、Atomic 等状态不可替换的时间；
- (A)：相联度。

L2 服务更多 SM，确实可能增大 (\lambda_{\text{set}})；但与此同时：

- L2 有多个 Subpartition；
- 每个 Subpartition 有多个 Set；
- 地址 Hash 会分散请求；
- L2 相联度通常高于 L1；
- 每个 Warp 在到达 L2 前通常已经拆成独立 Sector/Cacheline 请求。

因此，SM 数量本身不能推出 Set Stall 更严重。

当前 QV100 配置并不是“典型 16 路”，而是每个 L2 Subpartition：

- 32 个 Set；
- 24 路；
- 128B Cacheline；
- Sector Cache；
- 每个 Cacheline 含四个 32B Sector；
- 32 个内存通道，每通道两个 Subpartition；
- 全芯片共 6MB L2。

所以论文中不要把“L1 4 路、L2 16 路”作为固定事实，更不能据此推导瓶颈。应该测量：

- 每个 Subpartition 的请求速率；
- 每个 Set 的瞬态 Way 数；
- `all ways reserved/non-replaceable` 的周期比例；
- Set 压力的 P50、P95、P99，而不只是全局平均值。

### SIMT 发散在 L2 中扮演什么角色

SIMT 发散仍然重要，但作用与 L1 不同：

- 在 L1，问题是“一条 Warp 指令同时依赖多条 Cacheline，最终等待最慢的一条”；
- 到 L2 时，它们通常已经是多条独立 Sector/Cacheline 事务；
- 因而在 L2 中，SIMT 发散主要制造**突发到达、Bank/Set 偏斜和大量独立在途事务**，不再直接对应一个 PIB 项或 Warp 等待计数器。

所以 L2 论文应写：

> Warp 级不规则访存产生突发的 Sector 事务流，多个 SM 的事务在共享 L2 汇聚，使瞬态存储和 Set 分配压力具有高度突发性。

而不应写：

> L2 也要等待一条 Warp 的 32 条 Cacheline 全部返回。

后者属于 L1/SM 端完成语义，不属于 L2 的直接管理职责。

------

## 2. “L2 延迟可以达到上千拍”

**作为端到端 L2 Miss 或高排队条件下的尾延迟可以成立，但不能称为 L2 Hit Latency。**

论文自己的 Re-Hot 实验中，将 L2 平均访问延迟描述为约 200 周期。

当前 QV100 配置则使用：

- `gpgpu_l2_rop_latency = 160`；
- `dram_latency = 100`；

此外还会叠加 NoC、L2 Queue、DRAM 调度、Bank 冲突和返回排队。

因此，正确表述是：

> L2 Hit 本身通常是数百周期量级；L2 Miss 加上 NoC、DRAM 和排队后，端到端事务寿命可达到数百至上千周期。长事务寿命使 Miss 发出时的物理资源预留长期占用，从而放大 Early Binding 的代价。

这恰好支持 **Transaction–Payload Decoupling**，但不能用“L2 Hit 上千拍”来做动机。

------

## 3. “L2 需要 WBUF”

**功能上正确，但结构上不能简单假定。**

对于写回 L2，脏受害者被替换后，在数据成功交给下层之前，系统必须保存：

- 地址；
- Dirty Sector/Byte Mask；
- 数据载荷；
- 顺序与事务状态；
- 下层注入和重试信息。

这些状态可以位于：

- 专用全数据 Writeback Buffer；
- L2 Data Array 原位置；
- Victim/FRC；
- 共享 Transient Pool；
- 下一级请求队列。

所以“需要写回事务状态”是必然的，但“必须有一个独立、固定项数、完整 128B 的 WBUF”不是必然的。

当前 Baseline 事实上已经支持：

- 128B Cacheline；
- 4×32B Sector；
- Dirty Sector Mask；
- Dirty Byte Mask；
- 按实际脏数据量计算写回大小。

Baseline 的带宽模型还会根据脏数据大小，占用 L2 Data Port 来读出写回数据。例如 32B Data Port 下，完整 128B 脏行要占用四个周期，但只有一个脏 Sector 时只需一个周期。

因此，“Cacheline 为 1024bit，所以 WBUF 通常只能做几项”目前没有证据。当前自定义模型的默认 WBQ 恰好是四项，但这只是实验参数，不是现实 GPU 的公开硬件事实。

论文动机不能写成：

> 128B 太宽，所以 WBUF 只能有几项。

更稳妥的动机是：

> 固定容量的全数据 Writeback Storage 会造成容量分区、额外数据搬运和突发写回压力；其性能代价不仅来自存储位数，也来自 Data Port、Bank、下层注入和生命周期管理。

------

## 4. “利用解耦 Data Entry 去掉 WBUF”

这个方向**有价值，但上一轮的表述偏乐观，需要改成‘原地退役＋小型逃生缓冲’**。

### 原地写回能省什么

传统 Copy-out 路径可能是：

```text
Resident Dirty Entry
        ↓ 读取
Dedicated WBUF
        ↓
NoC / Memory
```

原地退役可以变成：

```text
Resident Dirty Entry
        ↓ 解除Resident Tag映射
WB_PENDING Entry（仍在原物理位置）
        ↓
NoC / Memory
        ↓
FREE
```

它可以减少：

- 对专用全数据 WBUF 的容量需求；
- 向 WBUF 写入和从 WBUF 再读取的内部数据搬运；
- Resident Data 与 Writeback Data 的静态容量划分。

但它**不能省掉将数据从 SRAM 读出并发送给下层的操作**。更重要的是，原地写回会让原物理 Entry 在下层拥塞期间持续被占用。

因此它是一种明确的权衡：

| Copy-out WBUF               | 原地退役                      |
| --------------------------- | ----------------------------- |
| 需要额外全数据 Buffer       | 不需要或只需很小 Buffer       |
| 可以较早释放 Resident Entry | Dirty Entry 长时间占用 Pool   |
| 有数据复制和额外写入        | 减少中间数据搬运              |
| WBUF 满时阻塞               | Pool Transient Entry 多时阻塞 |
| 容量静态划分                | 容量可动态共享                |

### 更好的设计：Adaptive In-place Retirement

不要彻底删除 WBUF，而是保留一个很小的 **Emergency Spill Buffer**：

- Pool 压力低、Writeback 能快速发送时：原地退役；
- Fill 返回压力高、急需释放物理 Entry 时：将少量脏 Sector Copy-out 到 Spill Buffer；
- 下层写通路堵塞时：给 Writeback 保留独立 Credit；
- 只有在死锁或前向进展需要时才使用专用 Buffer。

这样论文可以声称：

> 消除常见路径上固定划分的大容量全数据 WBUF，并将小型专用 Buffer 降级为保障前向进展的逃生路径。

而不是声称：

> 完全不需要任何 Writeback Buffer。

这既更真实，也更容易实现无死锁。

------

## 5. “Bypass Read/Write 也使用 Data Pool”

### Bypass Read：只在必要时落池

对真正的 No-allocate Read，如果：

- 只有一个请求者；
- NoC 返回通路畅通；
- 不需要合并或重排；

最佳路径通常是：

```text
Memory → L2 Response Path → L1/SM
```

若强制写入 Data Pool，再从 Pool 读取返回，会增加：

- 一次 SRAM 写；
- 一次 SRAM 读；
- Data Entry 占用；
- Data Bank 能耗和端口压力。

所以应该采用：

> **Direct Forward by default，Conditional Materialization when needed。**

只有在以下情况才落入 Pool：

- 多个请求者需要同一返回；
- 目标 SM/L1 暂时无法接收；
- 返回 NoC 反压；
- 需要 Multicast；
- 多个 Sector 分批到达，需要暂存和组装；
- 请求可能被动态提升为 Cacheable。

### Bypass Write：比 Bypass Read 更值得池化

部分写请求可能只覆盖一个或几个 Sector。共享池可作为：

- Store Gathering Entry；
- Write Combining Entry；
- Dirty Sector Buffer；
- 后续动态提升为 Resident Dirty Line 的候选。

这一方向比 Bypass Read 更合理。

### 当前 Trace 环境的实际限制

当前 Trace-driven Decoder 中，带 `BYPASS` 或 Strong GPU Scope 的 Load 会被设置成 `CACHE_GLOBAL`，代码注释明确表示这是**绕过 L1**；Atomic 也被设置为 `CACHE_GLOBAL`，即到 L2 执行。当前路径没有清晰表达“绕过 L2、直接访问内存”的独立属性。

因此，现阶段：

- 可以研究 L1-bypass、L2-cacheable 流量；
- 不能直接声称已经覆盖真实 L2 No-allocate Bypass；
- 若要让 L2 Bypass 成为核心贡献，必须先扩展 Trace 格式、Opcode 解析和 `mem_fetch` 属性。

所以我建议第一版论文不要把 Bypass 作为主贡献。

------

## 6. “Atomic 是瓶颈，Elastic Pool 可以优化 Atomic”

**只对一部分 Atomic 瓶颈成立。**

Elastic Pool 可以缓解：

- 不同 Cacheline 的大量 Atomic 同时占用 L2 Entry；
- Atomic-locked Line 长时间占住 Resident Way；
- Atomic、Fill、WB 之间固定存储容量不均衡；
- Atomic 突发导致的瞬态 Entry 不足。

但不能解决：

- 大量 Atomic 访问同一个地址；
- 同一 Cacheline 上必须串行的读改写；
- Atomic Unit 运算吞吐量不足；
- 内存一致性和顺序约束。

如果 10,000 个 Atomic Add 都访问同一地址，物理池再大也只需要一个 Cacheline，瓶颈完全在同地址序列化和 Atomic Unit。

已有 Atomic Cache 将原子运算放入 Cache Array 内执行；ARC 则利用 Warp 内同地址局部性，在 SM 端先做 Reduction，降低发送到 L2 Atomic Unit 的请求量。它们解决的是运算和同地址序列化，而不是物理数据 Entry 的生命周期。([dblp](https://dblp.uni-trier.de/pid/09/4195.html))

更重要的是，当前自定义 L2 后端不模拟实际数据和原子计算，只让现有 GPGPU-Sim 功能回调完成 Atomic 语义；模型文档也明确说明没有 Data/ECC Array 和 Byte-accurate Atomic。

所以第一阶段应当：

- 正确保持 Atomic 的 Baseline 语义；
- 测量 Atomic 对 Pool、Set 和 Queue 的占用；
- 不把 Atomic Throughput Optimization 作为主贡献。

若 Characterization 表明 Atomic Queue/Entry Pressure 明显，再扩展为第二项工作。

------

## 7. “Resident、Fill、WB、Bypass、Atomic 共用一个 Data Pool”

**原理成立，但只有在各类需求峰值不完全同步时才有收益。**

设不同事务类型的瞬态占用为 (O_i(t))。

静态划分需要的容量近似为：

# [ C_{\text{static}}

\sum_i \max_t O_i(t)
]

共享池所需容量至少为：

[
C_{\text{pool}}
\ge
\max_t \sum_i O_i(t)
]

只有当：

[
\max_t \sum_i O_i(t)
\ll
\sum_i \max_t O_i(t)
]

共享池才会显著节省容量或减少 Stall。

如果 Fill、Writeback 和 Atomic 总是在同一阶段一起爆发，那么池化不能创造容量，只能改变谁先阻塞。

因此，论文最重要的 Characterization 之一不是平均 Occupancy，而是：

- 各类 Occupancy 的时间序列；
- 峰值是否错开；
- 两两相关系数；
- 某一专用结构满时，其他结构或 Resident Entry 是否确实空闲。

这是共享池故事能否成立的直接证据。

# 二、创新性边界：哪些已有工作已经做过

## 1. Delayed Victim Selection 已被 FRC 做过

FRC 已经观察到 GPU L2 的突发 Miss 会让受害者处理和 Fill 串行化。它使用额外的 Fetch and Replacement Cache 保存到达数据和控制状态，在数据取回后再与 LLC 受害者交换，并延后受害者驱逐。也就是说：

- 延后选择/处理受害者；
- 让 Fill 不直接占用目标 LLC Way；
- 使用额外临时数据存储；

都不是新的。([扎关](https://zaguan.unizar.es/record/84363))

因此不能把下面这句话作为主创新：

> 数据返回时再选择受害者。

它最多是设计基础。

## 2. Tag–Data Decoupling 不是新思想

NOMAD 已经通过 Tag–Data Decoupling 实现 Non-blocking OS-managed DRAM Cache：Tag 可以先更新，而数据仍在搬运，后端另行跟踪数据是否到达。([Yonsei University](https://yonsei.elsevierpure.com/en/publications/nomad-enabling-non-blocking-os-managed-dram-cache-via-tag-data-de/))

更早还有 Decoupled Sectored Cache 等工作；原博士论文参考文献本身也列出了这条研究线。

因此不能写：

> 首次将 Tag 和 Data 解耦。

## 3. 动态 MSHR 和 Cache/MSHR 共享也不是新思想

DL-MSHR 从共享 Slot Pool 动态组成 MSHR，使 Primary Miss 多和 Secondary Miss 多的应用都能按需使用资源。([dblp](https://dblp.org/rec/conf/ics/GuC19.html))

MiCache 进一步让 Cache Entry 和 MSHR Entry 共享存储空间，根据执行阶段动态调整二者容量。([GitHub](https://github.com/CGCL-codes/MiCache))

所以也不能只写：

> 将 Cache Entry 和 Miss Tracking Entry 统一。

------

## 4. 推荐的创新边界

当前检索中，我没有发现一项工作完整同时具备以下组合，但这仍然只是**暂定创新边界，不是“首次”的最终证明**：

1. **GPU L2 Transaction–Payload Decoupling**：长延迟事务只占 TD Metadata，不提前绑定完整物理数据位置；
2. **Late-bound Resident Installation**：数据到达后才决定是否缓存、替换谁、放在哪个物理 Entry；
3. **In-place Dirty Retirement**：脏行解除 Resident Tag 后继续使用原物理 Entry 完成写回；
4. **Adaptive Spill**：Pool 压力高时才使用小型 Writeback Spill Buffer；
5. **Bank-local Elastic Payload Pool**：Resident、Fill 和 WB 动态共享，而不是固定 FRC/WBUF；
6. **Sector-aware Lifetime Management**：保留 32B Sector 和 Byte Mask，必要时支持部分 Sector 提前释放；
7. **Address-ordered Transaction Directory**：统一处理同地址 Read、Write、Fill、WB 和 Atomic 的合并或串行；
8. **Deadlock-free Landing and Writeback Credit Protocol**。

这八项不需要全部在第一版中实现。论文的必要核心可以收缩到前五项加正确的 Sector 语义。

------

# 三、建议重构成什么论文故事

建议暂定名称：

> **LateBind-L2: Late-Bound Placement and In-Place Retirement for GPU L2 Caches**

中文可以是：

> **LateBind-L2：面向 GPU 二级缓存的延迟绑定与原地退役数据管理**

## 1. 核心问题不再是“Buffer 太小”

更好的问题定义是：

> 传统 GPU L2 在 Miss 发出时，同时过早决定了三个本应分离的问题：
> ① 该请求占用哪个 Resident Set Way；
> ② 返回数据使用哪个物理 Data Entry；
> ③ 被替换脏行如何转移到 Writeback 路径。
> 当 Miss 生命周期达到数百甚至上千周期时，这些早期决策会长期预留没有有效 Payload 的 Entry、过早驱逐仍可能被重用的受害者，并在 Resident Data 与多个瞬态 Buffer 之间形成容量碎片。

这样一来：

- 长延迟；
- Set Transient Blocking；
- WBUF；
- Fill；
- 数据池；

都围绕一个统一的 **Early Binding** 问题展开。

## 2. 推荐的硬件结构

每个 L2 Subpartition 独立包含以下结构。

### Resident Directory，RD

保持 Baseline 的 Set 和 Associativity：

```text
{tag,
 physical_line_id,
 valid_sector_mask,
 dirty_sector_mask,
 byte_mask,
 replacement_state}
```

RD 决定真正可被后续请求命中的 Resident Cacheline。

### Transaction Directory，TD

按地址或 `{line, sector}` 跟踪在途事务：

```text
{address,
 transaction_type,
 state,
 waiter_head,
 physical_line_id_or_null,
 sector_mask,
 byte_mask,
 ordering_state}
```

事务类型初期只需要：

- `FILL`；
- `WRITEBACK`；
- `WRITE_ALLOCATE`；
- `ATOMIC`，只用于维持正确顺序。

后续才增加：

- `BYPASS_RESPONSE`；
- `STORE_GATHER`。

TD 是重新设计后的 Miss Handling Architecture。不要声称它是 MSHR-free。

### Physical Line Pool，PLP

每个 Subpartition 或 Data Bank 有一个物理数据池：

```text
N 个Resident预算 + E个Transient Headroom
```

每个物理 Entry 的角色可以是：

```text
FREE
RESIDENT_CLEAN
RESIDENT_DIRTY
FILL_LANDING
WB_PENDING
STORE_GATHER
ATOMIC_LOCKED
```

关键是：

- RD 和 TD 都通过 Pointer 指向 PLP；
- PLP Entry 不永久属于某一种功能；
- 角色变化通常只更新 Metadata，不搬移完整数据。

### Waiter Node Pool

不要像原 L1 OO-DTC 那样给每条 Line 配一个与请求表等宽的 Dense Bitmap。

使用共享稀疏节点池：

```text
TD Entry → waiter_head → waiter_node → waiter_node ...
```

这样可适应：

- 很多地址、每个地址少量 Secondary Miss；
- 少数热点地址、大量 Secondary Miss；

也更接近 DL-MSHR 的动态资源思想。

### 小型 Emergency Buffer

保留：

- 每 Bank 1～2 个 Sector/Line 的 Return Landing Buffer；
- 每 Bank 1 个左右的 Writeback Spill Entry；
- 独立下层 Writeback Credit。

这些结构不是主数据存储，而是保证：

- Fill 到达一定有落点；
- Dirty Victim 可以前进；
- Fill 与 Writeback 不形成循环等待。

Baseline 代码明确禁止简单地把 Writeback Cache 改成 Allocate-on-fill，因为 Fill 需要驱逐脏行、Writeback 又可能因下层堵塞无法发出，两者会形成死锁。

因此，Late Binding 不能只是将配置从 `ON_MISS` 改为 `ON_FILL`；Landing Credit 和 WB Progress Rule 本身必须成为设计的一部分。

------

## 3. 典型执行流程

### Read Miss

```text
RD Miss
  ↓
TD Lookup
  ├─ TD Hit：合并为Secondary Miss
  └─ TD Miss：分配FILL事务并发送下层请求
```

此时：

- 不占用 Resident Way；
- 不分配完整 Data Entry；
- 只占用 TD 和必要的返回 Credit。

### Fill Return

```text
返回Sector
   ↓
获得Landing Entry
   ↓
此时才进行Admission和Victim Selection
   ├─ 不缓存：直接返回，随后释放
   ├─ Clean Victim：复用其物理Entry
   └─ Dirty Victim：原Entry转为WB_PENDING
                     新Fill使用Transient Headroom
```

安装 RD 映射后唤醒 Waiter。

### Dirty Eviction

常见路径：

```text
RD解除映射
物理Entry：RESIDENT_DIRTY → WB_PENDING
发送Dirty Sector
下层接受最后一个Beat后释放物理Entry
```

高压力路径：

```text
Pool即将耗尽
   ↓
将Dirty Sector复制到Emergency Spill
   ↓
立即释放原物理Entry给Fill
```

这比强制“永远原地”更稳健。

### 同地址重新访问

TD 必须能找到：

- 正在 Fill 的地址；
- 正在 WB 的地址；
- 正在执行 Atomic 的地址。

最简单、最安全的第一版规则是：

- 多个 Read 可以合并；
- Write/Atomic 与其他请求按到达顺序串行；
- WB 尚未发出时可取消并重新安装 Resident；
- WB 已发出后，Read 可以从仍在 Pool 中的 Payload Forward，新的 Write 等待 WB 达到规定顺序点。

论文展望部分本身也指出，Read 和 Write 走不同 NoC 通路时，同地址请求可能在 L2 反序到达。统一 TD 可以成为一个自然的逐地址排序点，但第一版只需保证 Per-address Ordering，不必宣称实现完整顺序一致性。

------

## 4. 第一版不要纳入全部功能

推荐按优先级划分：

| 优先级 | 功能                             | 是否进入主论文 |
| ------ | -------------------------------- | -------------- |
| P0     | Cacheable Read Fill              | 必须           |
| P0     | Dirty Writeback                  | 必须           |
| P0     | Sector/Byte Mask                 | 必须           |
| P0     | Same-address Merge/Ordering      | 必须           |
| P0     | Landing/WB Deadlock Protocol     | 必须           |

| P1     | Resident/Transient Dynamic Quota | 强烈建议       |
| P2     | Bypass Read Buffering            | 有证据再加     |

# 四、当前 GitHub 实现的完整审查

## 1. 值得保留的部分

当前实现已经提供了很好的基础设施：

- Framework 与 GPGPU-Sim 分离的 Worktree 管理；
- `baseline/fixed/decoupled` 后端选择；
- Token Table；
- AAD 和同地址合并；
- OTF Lower Read；
- WBQ；
- 抽象 Bank 仲裁；
- Resource Stall 计数；
- Debug Assertions；
- Provenance、可复现实验目录和 SHA-256 记录；
- Rodinia、Ubench、CUDA SDK 以及大型 Trace Archive 的运行脚本；
- AAD 满时优先推动 Lower Read 和 Writeback 的前向进展规则。

尤其是当前实现中：

> Writeback 和 Lower Read 的 Bank 仲裁优先于新 Tag 工作，避免 AAD 已满时新请求持续占用 Bank、反而让已有 Fill 永远无法发出。

这是一个正确且值得保留的 Deadlock/Progress 设计经验。

## 2. 不能用于正式性能结论的关键问题

### 2.1 当前模型实际上是全相联抽象模型

当前 `m_lines` 是按完整 Line Address 索引的映射结构：

- Hit 是地址是否存在于全局 `m_lines`；
- Eviction 是在所有 Line 中寻找最老项；
- 没有真实 Set；
- 没有 Associativity；
- 没有目标 Set 的 Reserved Way。

这意味着它从建模上直接消除了你最想研究的 Set-level Allocation Blocking。

而 Baseline QV100 是 32 Set、24 Way 的 Sector Cache。

所以当前模型不能回答：

- Set 冲突到底有多严重；
- 解耦后到底解决了多少 Set Stall；
- 收益来自 Pool，还是来自隐含的全相联化。

### 2.2 没有数据载荷和物理 Data Pool

模型文档明确指出：

- 不建模 Data Array；
- 不建模 ECC；
- 不保存实际 Cacheline 数据；
- 只建模 Metadata 和 Timing。

当前 `line_state` 也基本只有：

```text
dirty
last_touch
```

因此当前模型不能真正评估：

- WBUF 数据容量；
- Data Entry 动态复用；
- Copy-out 与 In-place 的 Data Port 代价；
- Sector Packing；
- Payload Landing；
- Data Bank 端口；
- Zero-copy 数据路径。

它可以验证控制状态，但不能验证论文核心。

### 2.3 忽略 Sector 和 Byte 语义

Baseline 是 128B Line、4×32B Sector，并跟踪 Dirty Byte Mask。当前模型按完整 128B Line 处理：

- AAD 按完整 Line 合并；
- OTF 按完整 Line；
- Writeback 按完整 Line；
- 没有 Sector Miss；
- 没有 Partial Write；
- 没有 Readable Sector 状态。

这会错误估计：

- MSHR 数；
- Secondary Miss 合并；
- 写回流量；
- Partial Write；
- Data Pool Occupancy；
- Bank 带宽。

正式模型必须至少保持 Baseline 的 Sector 语义，即使物理分配第一版仍采用完整 Line Envelope。

### 2.4 Write Miss 语义过于理想化

当前模型中，普通 Write Miss 可以：

- 直接安装 Line；
- 标记 Dirty；
- 不读取缺失的未写字节；
- 快速返回。

但 Baseline 的 `LAZY_FETCH_ON_READ`、`FETCH_ON_WRITE` 等策略需要处理：

- Byte Mask；
- 未写字节是否可读；
- 后续 Read 是否必须取回旧数据；
- Read-after-Write Pending；
- Partial Sector 状态。

因此当前结果对 Write-heavy Workload 不具备论文级可信度。

### 2.5 Atomic 状态与 Baseline 不一致

当前模型把 Atomic 排除在普通 Write 判断之外，更接近 Read Residency；而 Baseline 在 Atomic Fill 完成后会将对应 Cacheline 标记为 Modified，确保最终产生写回。

目前功能 Atomic 仍由 GPGPU-Sim 既有回调执行，但 Custom Backend 的 Dirty/WB 统计和资源状态可能与真实语义不一致。

### 2.6 Bank 模型过于抽象

当前使用：

```text
bank = line_number % number_of_banks
```

而不是：

- 实际 Subpartition Set Hash；
- Sector Bank；
- Data Array Bank；
- Tag/Data Pipeline；
- Pointer Indirection 后的 Bank 选择。

这可以作为早期压力模型，但不能用于最终 Bank Conflict 和 Critical Path 结论。

### 2.7 WBQ Stall 判断过于保守

当前逻辑大致上是在 Cache 满且存在任意 Dirty Line 时，就可能要求 WBQ 有空间，而不是先精确判断：

- 当前真正选中的 LRU Victim 是否 Dirty；
- Dirty Sector 数量；
- 是否有其他 Clean Victim；
- 是否能延迟选择受害者。

这会高估 WBQ Stall，也可能影响请求顺序。

### 2.8 资源规模没有等面积依据

当前默认：

- Request Token：512；
- AAD：256；
- Lower Read：32；
- WBQ：4。

Baseline 则是：

- 192 个 MSHR；
- 每个最多 Merge 4；
- 32 项 Miss Queue。

这些配置目前是功能参数，不是面积相等或现实硬件约束。最终论文必须按 Bit、端口和 Bank 数量对齐。

### 2.9 当前结果只能说明“模型能运行”

现有 Smoke 记录中：

- 部分测试略有加速；
- 部分测试略有下降；
- 多数测试接近 Baseline；
- 文档本身也将容量压力测试定位为前向进展和资源覆盖测试，而非代表性性能评估。

所以现有结果不能用来证明 LateBind 或共享池的收益。

## 2. 必须增加的统计

### A. Set-level Transient Pressure

每次 L2 Probe 时记录目标 Set 中：

```text
invalid_way_count
valid_clean_way_count
valid_dirty_way_count
reserved_sector_count
reserved_line_count
```

并记录：

- 所有 Way 都不可替换的次数；
- `LINE_ALLOC_FAIL`；
- 由于 Reserved 而阻塞；
- 由于 Dirty Victim/WB 下游而阻塞；
- 每个 Set 的最大同时 Pending 数；
- Set 压力的 P50/P95/P99。

### B. Payload-less Reservation

对每个 Reserved Sector 记录：

```text
reserve_cycle
first_data_arrival_cycle
fill_complete_cycle
```

计算：

# [ R_{\text{payloadless}}

\frac{\sum T_{\text{reserve→first-payload}}}
{\text{物理Sector数}\times\text{总周期}}
]

还要记录：

- 一个 Entry 已被 Reserved，但尚无任何有效 Sector 的周期；
- 只有 1/4、2/4、3/4 Sector 有效的周期；
- Pending 时间分布；
- Fill 返回突发度。

这是 Late Binding 最直接的 Motivation。

### C. MSHR 和 Secondary Miss

记录：

- MSHR Occupancy 时间序列；
- Primary Miss 数；
- Secondary Miss 数；
- Merge Degree 分布；
- MSHR Entry Full；
- Merge Slot Full；
- Read-after-Write Pending；
- 每个地址的 Waiter 数。

### D. Dirty 和 Writeback

记录：

- Dirty Victim 数；
- 每个 Dirty Victim 的脏 Sector 数；
- Dirty Byte 数；
- 从 Victim 选择到 Writeback 注入的延迟；
- L2 Data Port 因 Writeback 占用的周期；
- L2→DRAM Queue Full；
- 写回请求在下游停留时间；
- 同地址在 WB Pending 期间重新访问的比例。

### E. 事务类别 Occupancy

按固定窗口，例如每 1024 或 4096 个 L2 Cycle，记录：

```text
Resident Clean
Resident Dirty
Fill Pending
Fill Returned
Writeback Pending
Write Allocate
Atomic Pending
```

然后计算：

- 各自平均和峰值；
- 两两相关系数；
- 某一类别满时其他类别的空闲容量；
- 静态分区与共享池的理想容量差。

### F. Atomic

记录：

- Atomic 请求比例；
- 每个 Cacheline 的 Atomic 数；
- 同地址 Hotspot 程度；
- 不同地址并发 Atomic 数；
- Atomic 到达至完成延迟；
- Atomic Line 占用时间。

### G. Bypass

当前 Trace 首先只能统计：

- `CACHE_GLOBAL`，即绕过 L1、仍访问 L2；
- 普通 L2 Cacheable。

真正 L2 No-allocate 需要扩展后再统计，不要先把两者混为一谈。

# 七、第二阶段：先做 Oracle，而不是直接做复杂硬件

Characterization 后，依次增加以下理想模型。

## Oracle 1：Infinite MSHR

只扩大 MSHR 和 Merge Slot，回答：

> 性能是否主要受 Miss Metadata 限制？

## Oracle 2：No Set Reservation Blocking

允许在 Miss 发出时不因目标 Set 的 Reserved Way 而阻塞，但不改变 Hit Rate，回答：

> Set-level Transient Blocking 有多大上限？

## Oracle 3：Ideal Delayed Victim Selection

用无限 Landing Buffer，在 Fill 返回时才选择受害者，回答：

> Early Victim Selection 和 Payload-less Reservation 价值多大？

## Oracle 4：Ideal Writeback

分别测试：

- 无限 WBQ；
- Writeback 不占用 Data Port；
- Dirty Victim 可立即释放；
- Writeback 下层无阻塞。

这能分离：

- WBUF 容量；
- Data Port；
- 下层带宽；
- Dirty Entry 生命周期。

## Oracle 5：Equal-capacity Shared Transient Pool

总物理数据位不增加，只把 Baseline 中假定的：

- Fill Landing；
- Writeback Storage；
- Resident Data；

作为共享容量，回答：

> Pooling 本身是否有价值？

## Oracle 6：Sector-granular Pool

与完整 128B Line Pool 比较，回答：

> 真正收益是否来自 Sparse Dirty/Partial Sector，而不是简单的 Line Pool？

------

## Go/No-Go 判断标准

以下是工程门槛，不是理论定律：

### 继续完整 LateBind-L2

满足至少一项：

- 综合 Oracle 在访存敏感应用上几何平均提升约 8%～10%；
- 至少五个有代表性的应用提升超过 15%；
- Set Allocation、Payload-less Reservation、WB Stall 合计构成明显关键路径；
- 静态 Buffer 满时，其他类型物理空间经常空闲；
- Equal-area Shared Pool 明显接近无限资源上限。

### 收缩为单点工作

- 只有 Dirty WB 显著：做 **Adaptive In-place Writeback**；
- 只有 Set Transient Blocking 显著：做 **Delayed Replacement/FRC 改进**；
- 只有 Sparse Dirty Sector 显著：做 **Sector-granular Writeback Retirement**；
- 只有 MSHR 显著：做 **Banked Dynamic Transaction Directory**；
- 只有 Atomic 显著：转向 Atomic Combining/Reduction。

### 停止宽泛 Pool 方向

- 相关 Stall 合计低于约 2%～3%；
- 综合理想 Oracle 提升低于约 3%～5%；
- 各类瞬态峰值高度同步；
- Pooling 导致的 Resident 容量下降抵消全部收益；
- 真正瓶颈始终是 DRAM 带宽而非 L2 内部管理。

# 八、第三阶段：正式实现的推荐顺序

## 1. 先实现 FRC-like Baseline

由于 FRC 是最接近的已有工作，应先实现一个固定容量版本：

```text
4/8/16 Entry FRC per Subpartition
```

它应当：

- Miss 时只分配 Metadata；
- Fill 返回进入 FRC；
- 返回时选择 Victim；
- Dirty Victim 从 FRC/Writeback 路径处理。

这有三个作用：

1. 验证 Delayed Victim 模型；
2. 构建最重要的 Related Work Baseline；
3. 作为 LateBind-L2 的增量起点。

没有 FRC Baseline，审稿人很容易认为 LateBind 只是重新命名 FRC。

## 2. 再实现 Resident Directory + Physical Pool

先采用较简单的 **Line Envelope**：

- 物理 Entry 仍为 128B；
- 保持四个 Sector 的 Valid/Dirty/Byte Mask；
- TD 以 Sector 为事务粒度；
- RD 用一个 Physical Line Pointer。

这一版比真正任意 Sector Packing 更容易实现和综合。

## 3. 加入 Late Binding

Read Miss 时：

- 只分配 TD；
- 不占 RD Way；
- 不占 PLP Entry；
- 保留返回 Credit。

Fill 到达时：

- 分配 Landing；
- 选择受害者；
- 安装 RD；
- 唤醒 Waiter。

## 4. 加入 In-place Dirty Retirement

脏受害者：

```text
RESIDENT_DIRTY → WB_PENDING
```

RD Tag 被移除，TD 持有地址和物理 Pointer。

## 5. 加入 Adaptive Spill

基于以下信号决定原地还是 Copy-out：

```text
free_pool_entries
fill_return_queue_occupancy
wb_downstream_credit
bank_pressure
dirty_sector_count
```

例如：

```text
若 free_pool_entries > threshold 且 WB可快速发出：
    in-place
否则：
    spill
```

## 6. 加入 Dynamic Quota

每个 Pool 至少保留：

- Resident Floor；
- Fill Landing Guarantee；
- Writeback Progress Guarantee。

其余 Entry 在 Resident 和 Transient 之间动态竞争。

## 7. 最后才考虑 Sector Packing

如果 Characterization 表明大量脏行只有 1 个 Dirty Sector，可以进一步实现：

- Dirty Sector 单独退役；
- Clean Sector 立即释放；
- Writeback Beat 发送后逐 Sector 释放；
- 物理 Sector Slab。

这可能形成一个很强的 GPU 专属优化，但不应在第一版就增加实现风险。

```text
docs/l2_latebind_invariants.md
docs/l2_latebind_deadlock.md
docs/l2_latebind_stats.md
docs/l2_latebind_eval_plan.md
```

至少定义以下不变量：

1. 每个 `{address, sector}` 最多只有一个权威可写 Payload；
2. 每个 Sector 最多只有一个 Lower Read；
3. 所有 Secondary Read 都连接到唯一 TD；
4. Dirty Payload 在下层取得数据所有权前不得释放；
5. 每个已经发出的 Read 都有可证明的 Landing 路径；
6. Writeback 和 Fill 不允许形成循环资源等待；
7. RD Pointer 和 TD Pointer 不能同时错误地指向不同版本；
8. Write/Atomic 不得越过同地址的先前冲突事务；
9. FREE Entry 不得被任何 RD、TD 或返回队列引用；
10. 每个 Token 只能处于一个阶段。

建议状态：

```text
TD-only:
  FILL_PENDING_NO_PAYLOAD
  WRITE_WAITING
  ATOMIC_WAITING

Payload:
  FREE
  RESIDENT_CLEAN
  RESIDENT_DIRTY
  FILL_LANDING
  WB_PENDING
  STORE_GATHER
  ATOMIC_LOCKED
```

当前模型已有的 Token Ownership、AAD 唯一性和 Lower Read Priority Assertions 可以复用，但要扩展到 Physical Payload Ownership。

# 最终建议

L2 方向本身是合理的，但应做三项关键修正：

1. **不要以“L2 服务更多 SM、16 路不够”为核心动机**，而应量化 Set-level Transient Pressure；
2. **不要以“完全去掉 WBUF”为目标**，改成 Adaptive In-place Retirement，并保留小型 Spill/Emergency Path；
3. **不要一开始把 Bypass、Store、Atomic 全部纳入主贡献**，先做 Resident、Fill、Dirty WB 的 Late-bound Elastic Pool。

最适合写成论文的核心表述是：

> **GPU L2 的根本问题不是单一 Buffer 太小，而是长延迟事务在数据尚未到达时就过早绑定 Set Way、物理数据 Entry 和受害者写回路径。LateBind-L2 通过分离 Transaction 和 Payload，在 Fill 返回时才完成物理绑定，并通过原地退役与自适应溢出，使 Resident、Fill 和 Dirty Writeback 在保持 Sector 语义和前向进展的前提下动态共享物理数据资源。**

当前库不应废弃，但下一步应采用：

> **现有 Framework 与控制骨架继续使用；Characterization 和最终 Cache Model 从干净 Baseline 重新建立。**
