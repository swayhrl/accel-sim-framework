# 八、第 4 阶段 LateBind MVP：先把范围收窄

我建议 MVP 暂时不要做：

```text
Resident + Fill + WB + Bypass + Store Gather + Atomic Pool
```

这太大。

第一版 LateBind MVP 只解决：

> **Resident + Fill + Dirty Writeback 三者的 Transaction–Payload Decoupling。**

核心比较就变得非常干净：

```text
Conventional:
early victim binding

FRC:
dedicated transient FRC
+ delayed victim selection

LateBind:
no payload allocation before return
+ no dedicated FRC storage
+ in-place dirty retirement
```

------

# 九、LateBind MVP 的公平容量定义

这是现在就应该固定的。

假设 Baseline 每个 L2 slice 有：

[
N
]

个物理 Cacheline。

FRC-H：

[
N + H
]

个 Data Entry：

```text
N = L2 resident
H = dedicated FRC
```

那么 LateBind-H 也使用：

[
N+H
]

个 Data Entry。

但组织方式不同：

```text
Resident Directory capacity = N logical lines

Physical Line Pool capacity = N + H physical lines
```

所以：

### FRC

```text
N个位置只能Resident
H个位置只能FRC
```

### LateBind

```text
N+H全部进入统一Physical Pool

角色可以是：
FREE
RESIDENT
FILL
WB_PENDING
```

但：

> **MVP 中最大 Resident Tag 数仍然限制为 N。**

这样不会偷偷获得比 Baseline 更多的逻辑 L2 容量。

这是非常重要的公平性设计。

# 十、LateBind MVP 的四个结构

## 1. Resident Directory，RD

保持 Baseline：

```text
same nset
same associativity
same replacement policy
```

但每项变成：

```text
tag
valid sector mask
dirty sector mask
byte mask
replacement metadata
physical_line_id
```

关键是：

> Tag Way 和 Physical Data Line 不再固定绑定。

------

# 十一、2. Baseline MSHR 暂时保留

MVP **不要同时重做 MSHR**。

否则最后无法判断收益来自：

```text
Late Binding
```

还是：

```text
larger / better transaction tracking
```

所以：

```text
MSHR entries = Baseline
merge entries = Baseline
```

完全不变。

但给每个 Primary MSHR 增加一个很小的 placement metadata：

```text
LateBindTxn {
    target_set
    sector_mask
    physical_id = NONE
    state
}
```

这实际上是：

```text
Transaction exists
Payload does not yet exist
```

正好体现：

> Transaction–Payload Decoupling。

------

# 十二、3. Physical Line Pool，PLP

容量：

[
N+H
]

每个 Entry：

```text
FREE

RESIDENT_CLEAN
RESIDENT_DIRTY

FILL_LANDING

WB_PENDING
```

MVP 暂时不要加：

```text
BYPASS
STORE_GATHER
ATOMIC_LOCKED
```

后面再扩。

------

# 十三、4. Metadata-only Writeback Descriptor

Writeback 不再拥有固定全数据 WBUF。

只保存：

```text
address
physical_id
dirty_sector_mask
dirty_byte_mask
state
```

数据仍然留在 PLP。

也就是说：

```text
RESIDENT_DIRTY
       ↓
解除RD mapping
       ↓
WB_PENDING
```

原 Data Entry 不动。

这就是：

> **In-place Dirty Retirement**

------

# 十四、LateBind 的 Read Miss 流程

传统：

```text
Read Miss
 ↓
选择 victim
 ↓
reserve victim/data line
 ↓
发 DRAM read
```

FRC：

```text
Read Miss
 ↓
分配一个完整 FRC entry
 ↓
发 DRAM read
```

LateBind：

```text
Read Miss
 ↓
allocate MSHR
 ↓
allocate tiny LateBindTxn metadata
 ↓
physical_id = NONE
 ↓
立即发 DRAM read
```

此时：

```text
不占RD way
不占PLP data entry
不选victim
```

这是整个工作的第一核心点。

------

# 十五、Fill 返回：Clean Victim

假设：

```text
B returns
target set full
victim = A clean
```

LateBind：

```text
RD A → detach
       │
       ▼
直接复用 A 的 physical_id
       │
       ▼
写入 B
       │
       ▼
RD 安装 B → same physical_id
```

也就是：

```text
A physical line
       ↓ metadata rename
B physical line
```

不需要：

```text
FRC B ↔ L2 A
```

这种数据 Swap。

这是与 FRC 的第一个强区别。

------

# 十六、Fill 返回：Dirty Victim

假设：

```text
A dirty
B returned
```

如果 PLP 有 free physical line：

```text
A:
RESIDENT_DIRTY
      ↓
WB_PENDING
physical_id = P0

B:
分配 P1
      ↓
RESIDENT
```

即：

```text
P0 → old A, waiting writeback
P1 → new B
```

没有数据搬移。

这就是与 FRC 最大的第二个区别：

```text
FRC:
A 必须从 L2 交换/搬到 FRC

LateBind:
A 原地不动
只修改metadata owner
```

------

# 十七、没有 Free Physical Entry 怎么办

这必须在 MVP 中处理，否则一定会死锁。

推荐引入一个非常小的：

> **Emergency Spill Buffer**

例如：

```text
1 line / L2 subpartition
```

正常情况下不用。

如果：

```text
Fill B returned
victim A dirty
PLP free = 0
```

则：

```text
A dirty sectors
  ↓ copy
Emergency Spill
  ↓
A original physical entry free
  ↓
B install there
```

然后：

```text
Spill A → lower memory
```

所以：

```text
低压力：
in-place WB

高压力：
spill WB
```

这也就是未来的：

> **Adaptive In-place / Spill Policy**

MVP 先做固定规则：

```text
有free physical → in-place
没有free physical → spill
```

已经足够。

最终严格等存储比较时：

```text
LateBind PLP + Spill payload bits
```

必须与：

```text
L2 + FRC
```

一起核算。

------

# 十八、同地址 WB_PENDING 怎么处理

这是 MVP 必须定义，不然会出正确性漏洞。

例如：

```text
A 已经 WB_PENDING
新的 Read A 到来
```

第一版 MVP 不需要做 resurrection。

最安全的规则：

```text
lookup RD
miss

lookup WB descriptor
hit WB_PENDING
       ↓
stall / serialize this address
       ↓
等待WB ownership transfer完成
       ↓
重新执行request
```

以后可以优化成：

```text
forward
或
cancel WB + resurrect
```

但 MVP 不需要。

------

# 十九、Write / Atomic 的 MVP 策略

建议分两个开发层级。

## MVP-R0～R3

只对：

```text
Read miss
```

启用 LateBind。

Write/Atomic：

```text
走原baseline path
```

只用于 bring-up。

## MVP 最终退出前

必须支持：

### Partial write miss

仍使用：

```text
Baseline MSHR
Baseline byte mask
Baseline readable semantics
```

但对应 lower-read fill 使用 LateBind placement。

### Atomic

Atomic miss：

```text
LateBind fetch
→ fill/install
→ baseline atomic completion semantics
→ line becomes MODIFIED
```

不要重写 Atomic Unit。

也就是说：

> LateBind 优化的是 Storage Lifecycle，不优化 Atomic Compute 本身。

------

# 二十、LateBind 最重要的 Progress Rule

这里必须比 FRC 更严谨。

建议规定资源优先级：

```text
1. Existing WB progress
2. Returned fill
3. Existing lower read issue
4. New request admission
```

当：

```text
PLP free <= threshold
```

时：

```text
停止接纳新的primary miss
优先drain WB_PENDING
```

同时：

```text
lower read credit
```

不能把所有下层资源吃光，必须保留：

```text
writeback progress credit
```

这和当前 decoupled experimental backend 已经遇到过的 AAD-full deadlock 本质类似：旧事务必须优先于持续进入的新事务。

# 二十四、Stage 4 MVP 的 Exit Criteria 也建议提前写死

与 Stage 3 一样，不要靠“感觉做完了”。

至少：

| 指标                        | LateBind MVP 要求   |
| --------------------------- | ------------------- |
| LateBind disabled           | exact baseline      |
| Miss 时 RD reservation      | 0                   |
| Miss 时 PLP allocation      | 0                   |
| Fill-time victim selection  | 100% LateBind miss  |
| clean victim physical reuse | PASS                |
| dirty in-place WB           | PASS                |
| spill fallback              | PASS                |
| Sector/Byte correctness     | PASS                |
| Atomic correctness          | PASS                |
| Same-address ordering       | PASS                |
| Deadlock                    | 0                   |
| Lost dirty data             | 0                   |
| Duplicate lower read        | 0                   |
| Metadata-only lifetime      | >0                  |
| Internal data copy vs FRC   | 明显下降            |
| Pre-memory delay vs FRC     | 不应更差            |
| FRC-equivalent storage      | accounting complete |

最关键的不是一开始要求 IPC：

```text
LateBind > FRC 10%
```

而是先确认：

[
T_{\text{payload allocation}}
]

真的被推迟了，并且：

[
Bytes_{\text{internal copy, LateBind}}
<
Bytes_{\text{internal copy, FRC}}
]

以及：

[
TransientStorageEfficiency_{\text{LateBind}}

> 

TransientStorageEfficiency_{\text{FRC}}
]

如果这三条都没有发生，那么我们设计故事本身就不成立。

# 二十五、Branch 现在应该怎么组织

现在第 3 阶段还没正式开始的话，我建议比之前再规范一点：

```text

          │
          ▼
hrl/l2-common-missmgr-v1
          │

          │
     ┌────┴────┐
     ▼         ▼
```

而：

```text
hrl/l2-oracle-v1
```

继续独立从 Characterization 分出去。

### `l2-common-missmgr-v1` 中只能放：

- 公共统计；
- Miss 生命周期 timestamp；
- victim selection helper；
- fill hook；
- WB progress helper；
- directed test infrastructure。

**不能放任何 FRC 或 LateBind 特定行为。**

如果 Refactor 不需要，可以省掉这条 Branch；但只要 FRC 和 LateBind 都要改 `fill()`、victim selection、WB emission，我倾向于先做这个公共层。
