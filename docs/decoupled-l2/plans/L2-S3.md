第 3 阶段不能用“FRC 跑通了”作为完成标准。更合适的定义是：

> **FRC Baseline 已经成为一个可信的、论文可用的 reference implementation：机制忠实于 FRC 原文，保持我们 QV100 baseline 的其余 L2 语义不变，并且能够通过定向实验证明它确实产生了 FRC 应有的三个机制效应。**

FRC 原文明确把这三个效应定义为：延长 victim 生命周期、降低 L2 miss 的管理延迟、提高 MLP；如果 FRC 目标 set 无空闲 entry，则回退到 conventional miss path。

我建议把第 3 阶段和第 4 阶段按下面的标准固定下来。

------

# 一、第 3 阶段 FRC Baseline 的完成标准

可以把它分成 **6 个 Gate**。前 5 个全部 PASS，才能标记 `FRC_BASELINE_DONE`；第 6 个是论文级评估准备。

## Gate 1：Baseline Preservation

这是最硬的一条。

配置：

```text
-gpgpu_l2_frc_enable 0
```

时，相对于第 1 阶段 Characterization Baseline，要求：

```text
gpu cycle          完全相同
instruction count  完全相同
L2 hit/miss        完全相同
MSHR统计           完全相同
DRAM read/write    完全相同
writeback count    完全相同
atomic result      完全相同
最终程序输出       完全相同
```

不是 ±1%，而是 **exact match**。

如果关掉 FRC 都无法完全一致，说明实现已经污染了 baseline path。

### PASS 标准

> 所有 directed test + 至少一组 representative application regression 中，FRC-off 与 Characterization baseline 逐项一致。

------

# 二、Gate 2：必须复现 FRC 的四个核心行为

这是判断“实现的是不是 FRC”的核心。

## 2.1 Early Fetch

对于：

```text
L2 miss B
```

当目标 FRC set 有空闲 entry 时，必须：

```text
allocate FRC
→ immediately issue lower read
```

而在 B 返回之前：

```text
不允许 reserve L2 victim
不允许 invalidate victim
不允许提前产生 victim WB
```

原文明确规定 FRC 的作用就是先取新块，victim 的 invalidation/eviction 推迟到 fetch 之后。

### Directed Test

初始：

```text
L2 contains A
```

发：

```text
B miss
```

B 尚未返回时访问 A：

```text
A 必须仍然 L2 hit
```

### PASS

```text
frc_early_fetch > 0
victim_before_fill_invalidations == 0
```

------

## 2.2 Fill-time Victim Selection

FRC 不能在 miss 时锁定 victim。

应该是：

```text
B miss
 ↓
FRC B fetching
 ↓
...
B returns
 ↓
此时才重新选 L2 victim
```

FRC Figure 2 中正是返回后 swap，而不是 miss 时先把 victim 保留下来等着。

### Directed Test

在 B outstanding 期间不断访问原 LRU victim，使其 LRU 排名发生变化。

B 返回后应当选择**返回时真正的 replacement candidate**，而不是 miss 时保存的那个 victim。

### PASS

```text
miss_time_victim_binding == 0
fill_time_victim_selection > 0
```

------

## 2.3 FRC Fetch Hit / Secondary Miss Merge

假设：

```text
Req0 B → miss → FRC0 FETCHING
Req1 B → arrives later
```

必须：

```text
FRC hit FETCHING
→ MSHR merge
→ 不再发 second lower read
```

论文明确说，对正在 FRC 中 fetching 的 block 的 hit 要等原 Fetch 完成。

### 硬 Assertion

对于同一个：

```text
{cacheline, sector}
```

同时：

[
N_{\text{lower-read}} \le 1
]

除非由于正常 Eviction 后再次产生新的 generation。

------

## 2.4 FRC Set Full 必须退化到 Conventional Path

这一点不能做成：

```text
FRC full → RESERVATION_FAIL
```

原文规定：

> 如果目标 FRC set 没有 free entry，就按 conventional approach 处理。

所以定向测试必须强制：

```text
所有地址 → 一个 FRC set
FRC associativity = 4
连续 >4 个独立 miss
```

然后观察：

```text
前4个 → FRC path
第5个 → conventional L2 path
```

### PASS

```text
frc_set_full_fallback > 0
```

而且 fallback 后的行为必须与 baseline miss path 一致。

------

# 三、Gate 3：Clean / Dirty / Sector / Atomic 正确性

这一 Gate 是“FRC 不只是 Read-only toy model”。

## 3.1 Clean victim

```text
FRC B fetched
L2 victim A clean
```

应：

```text
B → L2
A → FRC
A无需WB
FRC立即free
```

------

## 3.2 Dirty victim

```text
FRC B fetched
L2 victim A dirty
```

必须：

```text
B → L2
A → FRC_EVICTING
        ↓
writeback A
        ↓
只有数据已经安全交给lower path后
FRC entry才可free
```

不能：

```text
swap
→ immediately free FRC
→ 后面再想办法写A
```

否则会丢脏数据。

------

## 3.3 Sector 语义

我们的 QV100 是：

```text
128B line
4 × 32B sector
```

因此要求：

- sector valid mask 正确；
- sector pending mask 正确；
- dirty sector mask 正确；
- dirty byte mask 与 Baseline 一致；
- partial write 不扩大成错误的 full-line write。

Baseline 本身已经按 Sector/Byte Mask 维护脏状态。

------

## 3.4 Atomic

最终 FRC Baseline 必须保持 Baseline Atomic 行为。

Baseline 在含 Atomic 的 MSHR 返回后会把对应 Cacheline 标记为 Modified。

所以 Stage 3 不能以：

> “Atomic 以后再说”

作为最终退出状态。

可以开发时最后做，但 `FRC_BASELINE_DONE` 前必须覆盖。

------

# 四、Gate 4：Forward Progress / Deadlock

这是论文级模型必须单列的一项。

至少需要下面这些 stress：

```text
FRC=1/4 entries
MSHR=minimum
L2→DRAM queue very small
DRAM→L2 queue very small
all-dirty target set
连续fill burst
连续dirty eviction
FRC set collision
atomic burst
```

要求：

```text
0 deadlock
0 assert
0 lost request
0 duplicate writeback
最终所有FRC entry = FREE
最终MSHR empty
最终WB path empty
```

特别是 Write-back + allocate-on-fill 一类机制很容易形成循环等待。现有 GPGPU-Sim 自己就明确禁止简单的 write-back `ON_FILL`，理由正是 Fill 等 Dirty WB、而 WB 又被拥塞路径阻塞可能造成死锁。

所以 FRC 以及后面的 LateBind 都必须拥有明确的 progress rule，而不是靠“实验没碰上死锁”。

------

# 五、Gate 5：必须出现 FRC 的“机制指纹”

这是最重要的性能前置验证。

**不要求复现论文的 25%/150% speedup。**

因为原论文是：

```text
AMD HD7770
64B block
16-way L2
Multi2Sim
```

而我们是 QV100-like Accel-Sim。

但必须复现下面四种趋势。

## 5.1 Victim Lifetime Extension > 0

统计：

# [ T_{\text{victim-life}}

## T_{\text{eviction}}

T_{\text{miss-trigger}}
]

FRC 相对 baseline 必须明显增加。

------

## 5.2 Pre-memory Miss Delay 下降

定义：

# [ T_{\text{pre}}

## T_{\text{lower-read issue}}

T_{\text{L2 miss arrival}}
]

Baseline 可能由于 replacement 阻塞：

```text
Tpre > 0
```

FRC 有空闲 entry 时应接近：

```text
Tpre ≈ arbitration delay
```

论文 Figure 6 所分析的就是排除实际内存访问时间后的 L2 miss delaying latency。

------

## 5.3 MLP 增加

在 Same-set Burst 定向测试中：

```text
baseline lower reads in flight = X
FRC lower reads in flight      > X
```

至少必须存在明确的定向 workload 能看到这一点。

------

## 5.4 FRC-served Miss Ratio 随容量总体增加

原论文专门画了：

```text
Percentage of misses served by FRC
```

并观察到容量增加后更多 Miss 能走 FRC 快路径。

我们的 sweep 至少做：

```text
4
8
16
32
64
```

最终论文再补：

```text
128
256
512
```

不要求 IPC 严格单调，因为更高 MLP 可能引起 DRAM contention；原论文自己就观察到 FRC 增大后部分 workload 的 miss latency 反而增加，因为更高并行度加重了内存竞争。

但：

```text
FRC-served ratio
available concurrent early-fetch capacity
```

应该表现出合理趋势。

------

# 六、Gate 6：什么时候才叫“论文可用的 FRC Baseline”

除了前面 5 个 Gate，再要求下面几项：

### 至少有：

```text
Baseline
FRC-4
FRC-8
FRC-16
FRC-32
FRC-64
```

### 并且有两种 FRC timing：

```text
Paper-faithful FRC
Conservative FRC
```

### 再有一个容量控制：

```text
Baseline + equivalent extra cache capacity
```

因为原论文也将 FRC 与简单增大 L2 容量比较，且发现 32～64 entry 的 FRC 常已达到较好性能。
