# hybridsort - source and behavior audit

This report is a read-only source/metadata audit. No GPU, native, capture or simulator execution was performed.

## 1. Program and algorithm

Sort FP32 values by a histogram-guided bucket stage followed by merge sorting within buckets. GPU histogram1024 bins -> CPU balanced pivots -> GPU bucket assignment/ranks/prefix -> CPU padding/offsets -> GPU scatter -> sort4 values/record -> repeated merges -> remove padding. Selected `r` constructs4194304 values from rand()/RAND_MAX and sorts the same CPU array four times (`main.cu:61-117`). Main does not call srand; exact libc/generated bytes are nevertheless not capture-input-SHA bound. File input500000 is a separate identity.

## 3. Host calls and kernel order

Each cudaSort copies N floats H2D, launches histogram1024Kernel and copies counts D2H. CPU computes pivots; H2D/bind pivot texture. GPU bucketcount -> bucketprefixoffset; D2H sizes; CPU computes padding/offsets and sends offsets H2D. GPU bucketsort -> mergeSortFirst -> repeated mergeSortPass -> mergepack; final N floats D2H (`main.cu:176-227`, `bucketsort.cu:84-151`, `mergesort.cu:20-106`). Seven unique global definitions. Selected trace has17 launches/sort: histogram,count,prefix,scatter,first,11 merge passes,pack; four groups give68. Pass count depends on largest padded bucket, not N alone. Optional VERIFY compares qsort result (`main:119-139`). OUTPUT writes original cpu_idata at159; that file is not itself a sorted-result checker.

## 4. Detailed kernel implementation

Histogram (`histogram1024_kernel.cu:76-113`) runs64 CTAs x96 threads. Each of3 warps owns1024 volatile shared bins; data-dependent updates use a threadTag retry idiom. CTA reduction combines the three histograms, then issues global atomicAdd per bin. bucketcount (`bucketsort_kernel.cu:30-66`) uses32 threads/CTA, shared1024 counters and data-dependent texture-pivot routing; writes encoded rank<<10|bucket and one1024-counter slab/CTA. addOffset is a volatile read/write/retry idiom, not CUDA atomicAdd. Prefix (`:68-80`) assigns one thread/bucket, scans CTA slabs, replaces counts with prefixes and writes totals. Scatter (`:82-104`) stages offsets and writes values to bucket+prefix+rank destinations.

mergeSortFirst (`mergesort_kernel.cu:54-65`) loads one float4 texture record/thread and sorts its4 values in registers with a fixed comparison network. mergeSortPass (`:67-140`) maps each thread to a pair of runs in a division; texture loads A/B and prefetches nextA/nextB, emits a lowest float4, retains the upper record and advances the chosen input until exhaustion. Run lengths/guards produce divergence. mergepack (`:142-150`) strips padding using constant constStartAddr, finalStartAddr and nullElems. No shared merge tile or barrier exists in these kernels. Volatile warp-counter correctness under the historical compiler/runtime is not certified from source alone.

## 5. Thread and address formulas

At N4194304, histogram data address is `BD+4*(96b+t+6144q)`: lane delta4B, iteration delta24576B; aligned full warp1 line/4 sectors. Atomic bin p is `BR+4p`; each CTA updates all1024 bins, so64 CTAs share the same addresses. Source issues65536 global atomicAdd calls/sort, even when a local bin sum is zero; this is a static count, not measured contention. Shared bin address is `Bsh+4*(1024*floor(t/32)+bin(value))`; retry iterations are data dependent.

Bucket count/scatter use tid=32b+t+32768q: lane delta4B for input/indice, loop delta131072B,128 iterations/thread. Pivot address logically `Bp+4*idx`; routing starts idx511 and halves the jump (`bucket kernel:46-55`). Prefix address=`Bprefix+4*(1024b+bucket)`: lane delta4B across buckets; same-thread CTA-scan delta4096B. Scatter destination=`Bout+4*(l_offsets[bucket]+prefix[b*1024+bucket]+rank)`, where rank=encoded>>10 and bucket=encoded&1023. Destination has no constant lane delta; exact line/sector coverage needs realized IDs/ranks. CTAs share pivots/totals but own prefix slabs.

First float4 texture/store address B+16tid gives512B/warp=4 aligned128B lines/16 sectors. Pass A address=`B+16*(constStartAddr[d]+localtid*nrElems+aidx)`, B adds nrElems/2 records. Adjacent lanes within a division initially differ16*nrElems B; aidx/bidx advance16B within each thread, conditionally. Output `B+16*(Astart+outidx)` is sequential per thread. nrElems2 means lane stride32B and32 sectors/8 aligned lines per full warp; nrElems>=8 starts lanes in distinct128B lines. Actual texture access/transfer semantics need binary/model evidence. Pack reads `Bin+4*(4*constStartAddr[d]+nullElems[d]+idx)` and writes `Bout+4*(finalStartAddr[d]+idx)`: lane delta4B inside a division, with alignment determined by padding. A warp straddling divisions uses distinct constant-array indices.

## 6. Dataflow, locality, coalescing and concurrency

Histogram and routing have strong shared/texture reuse plus explicit global atomics. Prefix exposes1024 independent threads with long serial scans. Scatter is irregular writing. Merge passes increase run length, alter lane stride, shrink useful concurrency and alternate two buffers; late geometry has a minimum8 CTAs. CPU round trips separate phases. Input is16MiB and prefix slabs4MiB, so whole-array L1 fit is inapplicable. Four sorts reuse CPU content but perform fresh allocations/copies, which does not prove warm device cache identity. Each merge output is the next pass input; residency and return lifetimes need timing evidence.
