# nn - nearest neighbors, two materially different GPU implementations

## 1. Program and algorithm
Compute Euclidean distance to a target latitude/longitude, then CPU selects k nearest records. Output is a CPU ranking of records and distances.2.0-ft streams fixed record windows and maintains k neighbors;3.1 loads/parses all files into FP32 locations then performs CPU partial selection. k changes CPU ranking work, not GPU distance formula. File order/content and parsing are part of identity.

## 3. Host and complete launch sequence
2.0-ft: validate argc>=6, open list/db, allocate once, `while(!done)` reads up to W records, advances files/sets done on short read, copies **W*49 bytes**, launches euclid over **W slots even for short/zero rec_count**, downloads W distances, CPU updates only rec_count records. Launch count is actual window-loop iterations, not simply ceil(total/W); file boundaries and exact-multiple EOF can add partial/zero windows. File/read failures exit before subsequent launches.3.1: parse CLI, load all records on CPU, clamp k<=N, check N against memory budget, launch one euclid, D2H and CPU `findLowest` O(k*N). ## 4. Unique kernel implementations
There is one kernel definition per version, but their signatures/data paths differ.2.0-ft euclid maps one thread/record, reads two five-character fields, parses digits/space conditions into registers and computes sqrt; block16, grid ceil(W/16).3.1 euclid maps `g=blockDim.x*(gridDim.x*by+bx)+tx`, loads two floats for g<N and stores one distance; block=min(device max,256), 2D grid derived from total blocks and maxGridX. No shared memory, barrier or atomic in either ([2.0-ft/nn/nn_cuda.cu:27](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/2.0-ft/nn/nn_cuda.cu#L27), [3.1/cuda/nn/nn_cuda.cu:49](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/nn/nn_cuda.cu#L49)).

## 5. Threads and address formulas
2.0-ft character addresses: `D+49*g+27+i` and `D+49*g+33+i`, i0..4; lane stride49B, same-thread next character1B; distance `Z+4*g`.3.1 location addresses `L+8*g` and `L+8*g+4`, distance `Z+4*g`.3.1 consecutive fields differ4B; next record8B. Different2D blocks flatten contiguously; extra blocks/threads guard g<N. These formulas derive directly from position arithmetic and LatLong layout ([2.0-ft/nn/nn_cuda.cu:31](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/2.0-ft/nn/nn_cuda.cu#L31), [3.1/cuda/nn/nn_cuda.cu:26](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/nn/nn_cuda.cu#L26)).

## 6. Locality, coalescing and concurrency
Coverage is computed as sets of `floor(byte_address/128)` lines and `floor(byte_address/32)` sectors, including every byte of each word. A32-lane, contiguous FP32/int32 aligned access occupies one line/four sectors; shifted alignment can require two/five. Active masks, generated instruction width and base alignment must be retained. Coverage does not prove cache hits, pending merges, DRAM transfers or simultaneous requests.

2.0-ft block16 means only16 active lanes per warp; per scalar character instruction each record49B apart gives16 distinct32B sectors, while successive character instructions can reuse sectors. The span of16 records is736B for a one-byte field; exact line count depends alignment. Do not calculate a fictitious full32-lane coalesced warp by combining two CTAs.3.1 per-field32-thread warp spans252B at stride8, covering typically8 sectors/two lines when aligned; the two fields jointly use every byte of256B. Repeated CPU windows reuse allocation addresses but carry different record data.3.1 streams one full dataset; neither implementation has inter-CTA data dependence. Parsing branches in2.0-ft add divergent masks and arithmetic; different kernels cannot share a single ordinary-global-memory characterization.

## 8. Source-established architecture features
Character strides versus compact FP32 AoS fundamentally alter spatial use; CPU parsing and top-k behavior move work across CPU/GPU boundary. GPU traffic has no atomic nearest-neighbor reduction.

## 9. Mechanism hypotheses
DTC-L1: per-character repeated line coverage may create short-term tag/data retention or pending-line opportunities; distinguish coalescing within an instruction from repeated accesses across instructions. EP-L2: compare stream-window reuse of physical buffers with all-at-once FP32 data, using bound captures and actual cache routing. k itself should not be used as a GPU load-intensity proxy.
