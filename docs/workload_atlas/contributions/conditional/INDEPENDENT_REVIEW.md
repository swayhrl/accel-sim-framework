## Coordinator address review: agreement with stated conditions

- ATAX/MVT row-thread accesses advance16384B between lanes and4B along a thread's loop. Their transpose accesses reverse these directions. BICG executes transpose/contiguous first, then row/strided; its kernel accumulators are initialized explicitly. ATAX's tmp/y initialization issue is real in the inspected source, separate from address geometry.
- A full32-lane instruction at row pitch4096 touches32 lines/32 sectors when lanes select different rows; aligned contiguous FP32 touches1 line/4 sectors. Footprint ratios32x line and8x sector do not equal observed bandwidth amplification. A strided warp's next loop step can reuse the same lines.
- 2DCONV's center tap1/4 and shifted taps2/5 are correct for aligned interior warp origin j0 multiple32. Nine-tap union contains3*34=102 FP32 values,408 useful bytes,9 lines/18 sectors; CTA8-row union is10*34=340 values,1360 bytes,30 lines/60 sectors. Adjacent row chunks include both left and right halos. Counting this union as nine issued instructions' transaction sum would be incorrect; the coordinator explicitly avoids that.
- GEMM's warp-uniform A and contiguous B addresses, with B's per-thread loop stride2048B, are correct for512 square/block32x8. Static A sharing across16 x-CTAs and B sharing across64 y-CTAs is an opportunity, without an overlap/hit assertion. C `+=` does not establish a SASS load/store every iteration.

## particlefilter_float: cross-CTA normalization/publication risk confirmed

Source uses double-valued weights/CDF/u despite the executable's float name. `threads_per_block=512` ([src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:14](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L14)); selected frozen `np1000` therefore implies two CTAs for the inspected host recipe ([src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:726](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L726)).

Each CTA normalizes only its local particle weights, then executes `__syncthreads`; global i0 immediately serially computes the CDF over **all** weights ([src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:266](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L266), [src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:98](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L98)). A CTA barrier cannot order another CTA's stores. Thus CDF construction can race other-CTA normalization and read pre-normalized values. This is a missing inter-CTA happens-before relation, not a claim that every execution necessarily sees stale data.

Global i0 also writes initial `u[0]` after constructing CDF; each CTA's thread0 reads `u[0]` after only its own CTA barrier and broadcasts it through shared u1. Nonzero CTAs can read u0 before block0 publishes it ([src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:282](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L282)). The allocated u buffer was not initialized/uploaded in the inspected first-frame setup ([src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:691](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L691), [src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:718](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L718)); subsequent frames can instead see the preceding frame's value. The later `find_index` launch boundary orders completion of normalization before resampling but cannot retrospectively repair a CDF/u value computed using unordered reads ([src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu:735](https://github.com/accel-sim/gpu-app-collection/blob/dad09cb0487845edc7524ded814c6cde9f0ef6a1/src/cuda/rodinia/3.1/cuda/particlefilter/ex_particle_CUDA_float_seq.cu#L735)).

These two risks disappear as cross-CTA issues when Nparticles<=512 and the entire grid is one CTA. They are activated by the selected-source np1000 launch recipe. Exact historical ELF/source binding is still absent, so **do not declare recorded native values incorrect or revise accepted science**. No disagreement with Rodinia agent's source-risk observation.
