# Compiler-native attribution candidate — feasibility contract, not execution authorization

The only candidate considered here is **`COMPILER_NATIVE_ATTRIBUTION`**: combine already-generated compiler artifacts with an unmodified runtime CUDA timeline. Do not install runtime model hooks, change vLLM/Qwen, insert a marker/custom op into a compiled graph, force a graph break, disable compilation, add per-module Events or start a simulator. This document authorizes no capture or Stage A V2 run.

## Existing and missing authority

- The accepted Mode A/B canary `9122fac5...` reports MODE_B compile-cache paths, file counts and content hashes (`COMPILE_CACHE_IDENTITY.json`) plus actual CUDA kernel-name inventories (`BACKEND_KERNEL_IDENTITY.tsv`, `KERNEL_INVENTORY_SHA256.json`). For MP02 MODE_B the receipt lists 346 pre-existing cache files; MP03 MODE_B lists two newly generated cache files. These receipts show that compiler artifacts may be available at the pinned runtime, but the review pack does **not** contain a verified per-kernel FX/IR/source-to-module mapping or a legal quantitative semantic timeline.
- `c48331a9...` stopped before kernel inventory or NSYS. Its zero V2 ranges are not a substitute for a CUDA kernel timeline. Historical MODE_C semantic fractions cannot be transferred to compiled MODE_B.
- A future Lane7 feasibility audit may inventory **already-created** FX/Dynamo graphs, Inductor IR, generated source, kernel names, source/module stack metadata and compile-cache metadata at the exact pinned cache paths. It must bind their raw bytes/SHA, specialization, source revision, shape and compile-cache provenance. It may use an **unmodified** same-run CUDA API/kernel sequence with names/timestamps if such an accepted timeline exists or is separately authorized later; this design does not launch one.

## Required mapping proof

Build an auditable kernel-instance table with at least `point_id`, `runtime_mode`, `request/step identity if proven`, `runtime kernel instance ID`, launch order and timestamp domain, generated kernel identifier, compiler artifact SHA/path, source/module stack anchor, assigned semantic family, optional layer/step, ambiguity class and coverage status. Join runtime instances to compiler artifacts by stable generated identifier plus exact specialization/cache provenance; a substring match on a generic GEMM name is not proof. Track fused kernels with multiple contributing families as `MIXED` unless the compiler artifact provides a non-overlapping, attributable boundary. Preserve unassigned activity as `UNKNOWN`; never allocate it to a convenient family. Disclose the mapped fraction of the legal parent CUDA wall union and all unmatched instances.

**LEVEL_2_EXACT** requires a source-backed runtime-instance-to-semantic-family mapping with zero ambiguity for every claimed interval, plus unambiguous repeated layer/step identity when a boundary claim depends on it. Names reused across 36 layers or 32 forwards are insufficient by themselves. Only this level can support DQ4a producer→consumer boundary timing. **LEVEL_1_FAMILY_ONLY** requires a stable generated-kernel-family-to-semantic-family mapping across the relevant B1/B4 shapes, but admits unresolved layer/step order; it can support bounded DQ1 family aggregates and DQ3 `MEMORY_SERVICE_CANDIDATE` localization, not DQ4a. **LEVEL_0_UNRESOLVED** means even family assignment is ambiguous or artifact/timeline identity cannot be closed; it supports no quantitative decode semantic attribution. Tier0 native request timing, NCU profile duration and NSYS CUDA intervals are distinct measurement systems; none may be silently substituted for another.

The first Lane7 task, if separately authorized, is an artifact-feasibility audit, not a performance test: enumerate exact existing cache files, validate hashes/source-to-kernel metadata, check whether a same-identity unmodified CUDA timeline is already available, produce a small mapping/ambiguity sample and declare the achieved level **before** any Stage A V2 design. If no reliable family link emerges, record LEVEL_0 and stop observer construction. If only LEVEL_1 emerges, design may consider DQ1/DQ3 family-level questions; DQ4a becomes `NOT_IDENTIFIABLE_UNDER_COMPILED_PATH`. LEVEL_2 may reopen DQ4a only with a separate contract. No level alone establishes material headroom or a new mechanism.
