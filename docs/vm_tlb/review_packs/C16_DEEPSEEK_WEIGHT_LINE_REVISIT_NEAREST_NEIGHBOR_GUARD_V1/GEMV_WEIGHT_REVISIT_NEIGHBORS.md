# DeepSeek weight-line revisit: nearest-neighbor guard

Date: 2026-10-01. Scope: CPU/literature/source reading only. This is **not** a new DeepSeek trace audit or a reconstruction of cuBLAS internals. It does not infer a byte count, cache miss count, or timing opportunity from a line-revisit label. LR12's broad taxonomy is not repeated.

## Three non-interchangeable observations

For two dynamic warp loads with address intervals `[a,a+w)`, use the same frozen address namespace, instruction width, active mask, process/kernel/CTA/warp IDs and temporal order. Let `sector(a)=floor(a/S)` (`S=32 B` for the documented coalescing example on compute capability ≥6.0) and `line(a)=floor(a/L)`; a 128 B *analysis* line can be used only if that is the accepted C16 line convention, not assumed to be the physical DRAM transfer size. An interval crossing a boundary belongs to every touched sector/line.

| Class | Strict predicate | What it establishes | What it does **not** establish |
|---|---|---|---|
| `SAME_LINE_DIFFERENT_SECTOR` | Same line; disjoint sector sets | Two warps touch spatially adjacent line regions | No same-sector or same-byte repetition; no excess sector transaction follows. |
| `SAME_SECTOR_DUPLICATE` | Sector-set intersection, but byte-interval intersection may be empty | A 32 B sector is referenced in ≥2 warp events | Not necessarily duplicate useful bytes or ≥2 L2 misses/DRAM fills. |
| `SAME_BYTE_DUPLICATE` | Byte-interval intersection nonempty | Strictly repeated operand bytes | Not necessarily avoidable: different outputs/tokens may need them; cache may serve later requests. |

The categories are nested only with precise definitions: same-byte implies same-sector for the overlapping byte; same-sector does **not** imply same-byte. `SAME_LINE_DIFFERENT_SECTOR` explicitly excludes same-sector. Counting 128 B line IDs alone cannot adjudicate either duplicate class. CUDA coalesces **within** a warp to the needed 32 B sectors; it does not promise that all independent warp/CTA requests collapse into one transaction. See the [CUDA Best Practices Guide §10.2.1](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory). This distinction is the first novelty guard.

## Four questions answered from nearest neighbors

1. **Is same-line/different-sector cross-warp access a normal work-partition outcome?** It is a plausible and often benign consequence of splitting output rows/columns or K-tiles across warps, especially with packed layouts and 32 B transaction granularity; the literature/code does not establish its *frequency* for the frozen DeepSeek target. [AWQ's published GEMV source](https://raw.githubusercontent.com/mit-han-lab/llm-awq/d6e797a42b9ef7778de8ee2352116e0f48a78d61/awq/kernels/csrc/quantization/gemv_cuda.cu) maps `oc_idx` to warp-y and vector-loads packed weights while reducing within a warp. [CUTLASS GEMV source](https://raw.githubusercontent.com/NVIDIA/cutlass/0b55a2f691d69981583568fd9eb69687b1f0de8a/include/cutlass/gemm/kernel/gemv.h) exposes row/K thread mapping. Neither source says that matching line IDs imply wasted bytes. This is a structural inference from their mappings, not a measurement of DeepSeek.
2. **How is strict same-sector or same-byte reuse handled in software?** Within a CTA, cooperative load to shared memory followed by multiple warp consumers is mature; [MARLIN §3.4](https://arxiv.org/html/2408.11743v1) explicitly stages both operands in shared memory, uses `cp.async`, distributes K across warps and reduces partial outputs. [CUTLASS GEMM design](https://github.com/NVIDIA/cutlass/blob/0b55a2f691d69981583568fd9eb69687b1f0de8a/media/docs/cpp/efficient_gemm.md) uses CTA shared-memory tiles, sliced-K/split-K, tile rasterization and (on Hopper+) producer/consumer warp specialization. Across CTAs, shared memory cannot directly share a staged tile; software can alter decomposition or schedule to improve locality, while existing caches may already service requests. [GemLite](https://github.com/dropbox/gemlite/tree/89d9bc705c5dfca9115d3a5620f97a17ba0111a7) stages the reused **input vector** in shared memory and offers GEMV RevSplit-K; that is not proof it removes duplicated *weight* bytes.
3. **Are the requested named capabilities already present?** Yes, as a menu, not in every one kernel: CUTLASS supplies GEMV mapping, split/sliced-K, CTA shared staging and persistent/warp-specialized GEMM schedules; MARLIN combines cooperative weight staging, K-parallel warp work, partial reduction and striped SM assignment; [FLUTE §3.1–3.3](https://arxiv.org/html/2407.10960v3) restructures packed weights, loads tiles into shared memory and uses Stream-K, but is LUT quantization; [QUICK §3](https://arxiv.org/html/2402.10076v1) does the *opposite* of staging dequantized weights—offline interleaving permits direct register load to avoid shared-memory write-back and `ldmatrix`. cuBLAS documents GEMV/GEMV-batched **API semantics**, not its private warp/cache algorithm; `gemvX` strings found outside official documentation do not authorize an internal mapping claim. [vLLM's Marlin MoE path](https://raw.githubusercontent.com/vllm-project/vllm/bcee730b1a9d25f0fd283a0ef6c19133ebeebf4f/vllm/model_executor/layers/fused_moe/experts/marlin_moe.py) exposes expert grouping, `block_size_m` selection and reduction workspace, showing MoE-specific software partitioning exists, but does not prove the exact DeepSeek weight sector is coalesced.
4. **Cache mechanism or kernel dataflow?** A cross-warp *address* revisit is first a dataflow/partitioning and cache-service question. It becomes a cache-mechanism question only if the exact same-sector/byte demand survives strong format- and semantics-matched kernel variants, turns into measured lower-level traffic or exposed stalls, and has a positive whole-target oracle after staging, layout, synchronization, occupancy, reduction and added workspace costs. The read papers/source do not provide those DeepSeek-specific gates. `SAME_LINE_DIFFERENT_SECTOR` alone cannot motivate a new cache mechanism.

## Direct nearest-neighbor caveats

- [MARLIN](https://arxiv.org/html/2408.11743v1) is symmetric INT4 FP16×INT4 GEMM with a specific offline layout; it is not the same checkpoint/format/dispatch as any unprovided DeepSeek target. Its own §3.4 notes that *redundant scale reload from shared memory* can be faster than eliminating it because scheduling changes can cost 10–20% on some shapes. Fewer reads need not mean fewer cycles.
- [QUICK](https://arxiv.org/html/2402.10076v1) targets bank conflicts/dequantized weight write-back and is most relevant at larger batches; it does not document a same-sector cross-warp weight-dedup mechanism for batch-one MoE GEMV.
- [FLUTE](https://arxiv.org/html/2407.10960v3) is LUT-quantized, so its Stream-K/dataflow capability is a novelty neighbor, not a numerically interchangeable DeepSeek baseline.
- [CUTLASS's specific GEMV kernel](https://raw.githubusercontent.com/NVIDIA/cutlass/0b55a2f691d69981583568fd9eb69687b1f0de8a/include/cutlass/gemm/kernel/gemv.h) has an empty shared-storage union in the inspected specializations and performs global operand loads. Therefore “CUTLASS has CTA staging” is true for its GEMM family, **not** evidence that this GEMV specialization always stages weights. Conversely, one simple GEMV specialization does not show that software cannot do so.
- [cuBLAS GEMV documentation](https://docs.nvidia.com/cuda/cublas/index.html#cublas-t-gemv) specifies math and API shape but does not expose internal CTA/warp mapping or sector behavior. Internal `GEMVX` spelling is `UNVERIFIED_INTERNAL_SYMBOL`, not a separate published architecture result.

All author artifacts and kernels are `NOT_RUN`. No DeepSeek address stream, SASS, NCU, simulator or GPU data was read or generated in this stage. The `CAPABILITY_MATRIX.tsv` pins code authority and marks `UNKNOWN` rather than filling private implementations by guesswork.
