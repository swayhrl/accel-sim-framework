# D0 exact same-consumer qualification

TE v2.19.0 publicly exports `Float8CurrentScalingQuantizer` (`transformer_engine/pytorch/__init__.py`, documented in `docs/api/pytorch.rst`). The public quantizer was configured to TE's current-scaling E4M3 recipe defaults: per-tensor, `rowwise=True`, `columnwise=False`, no power-of-two scale. TE `Linear` source accepts a quantized input and skips online input quantization in that branch; it keeps the same cached weight and `general_gemm` consumer. This is TE source-supported behavior, not a custom FP8 GEMM.

Audit-only un-timed capture retained the exact `Float8TensorStorage` created by a normal A1 online call. That internal storage cannot itself be passed to the public `te.Linear` module; D0 instead uses TE's public quantizer to construct a `Float8Tensor`. Its FP8 bytes, inverse-scale bytes and E4M3 dtype match the captured online object exactly. The public D0 input is prepared **before** its measured interval. Both arms use `is_first_microbatch=False` with one frozen weight cache; its FP8 data, inverse scale and device pointer were stable. A1, F0 and D0 outputs were bitwise equal, including all three NSYS witness pairs and pre/post formal checks. The shared output SHA256 is `f0d76722af0d3f67e08ea67b2abf20217035fccadbf6014c90eb5f6847878e10`.

The only behavioral difference inside the primary interval is A1's current-scaling input representation preparation. NSYS shows four preparation launches in A1 and none in D0; both launch the same exact SM89 E4M3 GEMM. D0 therefore passes the exact-safe same-consumer diagnostic gate. It remains a *ready-representation diagnostic*: moving quantization before the boundary is not automatically legal in an online inference deployment.
