# Wrapper and runtime boundary

The first Stage-C paired acquisition (attempt0) used the Python `cagra.search` default `resources=None`. Stable source `python/cuvs/cuvs/common/resources.pyx` proves that this creates a fresh `Resources` handle and synchronizes it **on every call**. Its Q1 MULTI_CTA 512/1 median was ~301.33 ms for 256 searches, so it was preserved in raw but **not accepted as the strong-software timing authority**.

The same two frozen arms were then remeasured once with one reused default cuVS `Resources`, preallocated outputs and explicit per-query `resources.sync()`. With identical index, queries, search params, recall gate and alternating groups, the corrected MULTI_CTA median was **56.110419 ms/256 Q1 queries** (MAD 0.089072 ms); SINGLE_CTA was **704.184787 ms/256** (MAD 0.078683 ms). The magnitude of attempt0→attempt1 change establishes that resource lifecycle mattered; it is not a pure Python-overhead estimate because both runs include cuVS host planning and GPU execution. The different SINGLE/MULTI modes can perform different traversal work and have slightly different recall, so their ratio is not a hardware-mechanism response.

Matched characterization reused the same explicit MULTI_CTA 512/1 and `Resources`. Median Q1 complete host request time was **0.215450 ms**, while a complete Q32 batch took **0.530881 ms**. The Q32 256-query set completed faster in aggregate, which is an amortized throughput fact, **not** a single-query latency bound (`Q32/32` was never used for that). The recorded host submit interval represented ~99.75% of Q1 wall time, but cuVS may execute/synchronize GPU work inside this C API call. It is **not** a measured wrapper-only fraction, and no >=10% host/wrapper gate is asserted from it.

A custom nonblocking CUDA stream for GPU-event accounting exited before a valid matched sample; the stable default `Resources` stream was restored. Hence pure GPU-active time is `UNAVAILABLE` at Stage D. The scientific Stage-D STOP condition was met before the conditional Stage-E fallback: no material complete-request low-concurrency latency loss remained after the quality-qualified mature MULTI_CTA mode and resource reuse. The one permitted preallocated C/C++/C-API fallback, persistent control, NSYS and NCU were therefore **not started**. This does not assert zero host overhead or zero future optimization headroom.
