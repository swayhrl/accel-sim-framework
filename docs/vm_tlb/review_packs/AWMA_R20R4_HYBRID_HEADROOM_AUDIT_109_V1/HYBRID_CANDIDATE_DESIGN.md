# One CPU-only hybrid design for future review; no implementation/run

Fixed stage: accepted `_update_gradient_incremental` only. Fixed worker pool: 304. Fixed switch: `current active_count <= 304`. No threshold/worker search, second stage, new queue algorithm, future niter, host per-iteration read, changed solver math or altered stop predicate.

At `_solver_iteration` entry the existing one-element device `nsolving` is the current count of worlds not yet marked done. The selected gradient stage runs before `_solve_done` decrements it, so a tiny device predicate could write `late = (nsolving[0] <= 304)` without reading a 1024-element `ctx.done` list. In the **early** branch (`>304`), retain the original baseline selected-stage launch organization and do not build active IDs at all. In the **late** branch (`<=304`), build the same ascending list from current `ctx.done` and use the original accepted 304-worker H/blocked-Cholesky mapping; the remaining stage kernels, row/tile math and qfrc recovery remain unchanged. Both branches must be represented as device conditional graph bodies, not host-selected per iteration.

Installed Warp 1.15 source exposes `capture_if` on a one-element device `int32` condition and the accepted solver already uses `capture_while` on `nsolving`. A future bounded implementation could pass that existing device count into the selected stage, produce the predicate, and capture baseline versus worklist stage bodies. The **nested conditional within this exact solver graph has not been built or validated** in R20R4. Its capture/liveness, branch-specific SolverContext outputs, complete-solver numerical contract and all switching/list costs would be mandatory gates for a separately authorized experiment. If nesting cannot be expressed without changing the solver lifecycle, that future attempt must report `R20R4_HYBRID_IMPLEMENTATION_NOT_CLEAN` rather than inventing another switch/queue system.

O2's 11.77% is a zero-cost *upper bound* from separate B0 runs. The actual hybrid may show no gain once predicate, branch, list, worker and serialization costs are counted. No candidate was run, no new input generated and holdout remains sealed.
