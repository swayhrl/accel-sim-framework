# C16 V4 — Global-memory path coverage policy

## Purpose

Current formal evidence closes the complete set of NVBit-recognized direct `GLOBAL + MREF` static rows for each selected target. This is a strong and useful scope, but it is not automatically identical to all physical global-memory traffic generated by the kernel.

Before broad cross-model replication, qualify whether selected kernels also use memory instructions/pathways that source or sink global memory while not appearing in the current direct-GLOBAL-MREF selector.

## Audit inputs

For each representative target function/code object:

- exact code-object identity;
- complete disassembly/instruction listing for the selected function;
- NVBit instruction metadata for all instructions, not only selected MREF rows;
- existing static MREF map;
- existing NSYS/NCU evidence where available.

Do not infer completeness from one selected PC or from opcode names alone.

## Required classification

Every memory-relevant static instruction in the exact target function should be classified into one of:

1. `DIRECT_GLOBAL_MREF_CAPTURED`
   - current NVBit metadata exposes global memory space and a memory-reference operand;
   - included in the frozen direct MREF set.

2. `SPECIAL_GLOBAL_PATH_PRESENT`
   - instruction has plausible global-memory semantics but is not represented by the direct selector;
   - examples may include global-to-shared asynchronous/copy paths or architecture-specific special memory instructions if they actually appear in the exact code object.

3. `NON_GLOBAL_OR_INTERNAL`
   - shared/local/constant/register-only or otherwise irrelevant to global-address tracing.

4. `SEMANTICS_UNRESOLVED`
   - evidence is insufficient; preserve unresolved status rather than inventing coverage.

Do not hard-code an architecture list as proof. Use the exact SM89 code object's SASS and NVBit metadata. The names `LDGSTS`, async copy, TMA, etc. are examples of categories to inspect, not assumptions that they exist.

## Dynamic qualification

If `SPECIAL_GLOBAL_PATH_PRESENT` is found:

- determine whether it is actually executed in the selected occurrence;
- use a bounded canary or profiler evidence where possible;
- if address-bearing instrumentation is possible without changing the scientific workload, implement and qualify it;
- if it cannot be traced, retain the current formal evidence but scope it explicitly to `DIRECT_GLOBAL_MREF_COMPLETE_SET` and mark the omitted path.

A special path that is statically present but dynamically zero for the frozen occurrence may be recorded as `SPECIAL_PATH_ZERO_EXECUTION_PROVEN` if that zero is independently established.

## Formal evidence labels

Existing accepted evidence is not invalidated. Its scope is:

`MREF_SHARDED_COMPLETE_SET = complete direct NVBit-recognized GLOBAL-MREF static set for the selected exact function/occurrence.`

For future targets, add a coverage qualification field:

- `ALL_DETECTED_GLOBAL_PATHS_COVERED`
- `DIRECT_GLOBAL_MREF_SCOPE_ONLY`
- `SPECIAL_PATH_ZERO_EXECUTION_PROVEN`
- `GLOBAL_PATH_COVERAGE_UNRESOLVED`

Do not use `ALL_DETECTED_GLOBAL_PATHS_COVERED` until the full-function audit closes.

## Claim boundary

Even after all static global-memory paths are covered, separate MREF/path replays still do not establish cross-group hardware order, whole-kernel reuse distance, or a single physical absolute-VA stream unless those are captured in one shared address-space execution with appropriate ordering evidence.
