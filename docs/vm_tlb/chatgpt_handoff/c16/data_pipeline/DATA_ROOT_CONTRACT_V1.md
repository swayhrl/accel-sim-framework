# C16 Data Root Contract V1

## Role

This contract defines the long-term C16 AI-workload data plane reachable from new174/2239. It does not authorize GPU capture, historical raw import, model migration, or deletion from any source.

Accepted topology after old174 closeout:

- node109: GPU producer only;
- new174/2239: CPU ingest, verification, catalog, parsing, feature extraction, analysis;
- node164-backed mount visible from new174: long-term data storage;
- Git: code, schemas, manifests, receipts, catalogs/review metadata;
- old174: historical source only.

## Required directory layout

```text
c16_ai_workload_2239/
├── inbox/
├── raw/
├── provenance/
├── parsed/
├── features/
├── datasets/
├── catalog/
├── reports/
├── quarantine/
├── legacy/
└── tmp/
```

Semantics:

- `inbox/`: incomplete receives only; run directories use `<RUN_ID>.partial` until independently verified.
- `raw/`: immutable admitted raw evidence. No in-place editing.
- `provenance/`: manifest, transfer receipt, source hashes, environment/model/input/capture binding per run.
- `parsed/`: deterministic parser products tied to a raw run.
- `features/`: derived page/cache-line/object/reuse/kernel summaries.
- `datasets/`: cross-run analysis inputs.
- `catalog/`: authoritative dynamic-data index for C16.
- `reports/`: non-raw reports and bounded review exports.
- `quarantine/`: failed verification, collisions, incomplete or ambiguous imports.
- `legacy/`: separately admitted historical datasets such as RTX4080 R5 or RTX3090 comparison material.
- `tmp/`: disposable analysis scratch; never authority.

## Raw admission invariant

Future admission must follow:

```text
receive into inbox/<RUN_ID>.partial
→ close writer
→ verify required files + size + SHA256 + manifest
→ same data-root promotion into raw/<RUN_ID>
→ write provenance/TRANSFER_RECEIPT.json
→ register catalog
→ emit ACK
```

Never copy directly into `raw/`. Never overwrite an existing `raw/<RUN_ID>`.

## Phase-B storage admission gates

The root is accepted only after an isolated fixture demonstrates:

1. root path resolves to the intended mounted filesystem;
2. directory creation and permissions work;
3. small file write/read/hash match;
4. file fsync behavior is recorded;
5. rename within the root succeeds without overwrite;
6. inbox-to-raw same-root rename semantics are demonstrated on an admission fixture;
7. reopened destination size/SHA256 match;
8. a bounded medium file write/read/hash test succeeds;
9. fixture cleanup succeeds;
10. no pre-existing user data is overwritten.

Directory fsync may be unsupported on SSHFS/FUSE. If so, this is not automatically a block provided file close/fsync, rename, reopen and independent hash/size verification pass. The limitation must be recorded and later pipeline V1 must compensate with manifest verification and ACK.

## Allowed Phase-B persistent writes

Only:

- the required directory skeleton;
- a header-only catalog;
- a small root/admission receipt under `provenance/`;
- review metadata generated by the admission itself.

No model, RTX3090 trace, RTX4080 R5 artifact, NCU report, NVBit raw trace, parsed dataset, or large scientific artifact may be imported in Phase B.
