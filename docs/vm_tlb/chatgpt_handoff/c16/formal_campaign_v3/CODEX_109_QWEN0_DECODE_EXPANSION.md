## V3 address-context hardening

Each MREF shard is a replay and may live in a different CUDA VA space. Therefore every shard must carry an address-space sidecar generated from the same process as the trace.

Required per-shard metadata artifact, suggested `ADDRESS_CONTEXT.json`:

- schema/version;
- run/target/static-MREF identity;
- process-local `address_space_id` unique to that CUDA process;
- GPU UUID;
- target process PID/start time for provenance;
- model/input/scenario identity;
- exact object/allocation ranges available **inside that same process**;
- parameter/buffer storage ranges;
- KV cache ranges at the selected phase/step where available;
- allocator/runtime ranges or snapshots if available without changing execution semantics;
- base-address alignment information needed for 4K/64K/2M interpretation;
- SHA binding to the shard trace and static map.

Do not use an object map generated by a different process to classify absolute GPU VAs.

If same-process object capture cannot be added cleanly to the current runner, preserve raw addresses but classify object semantics as UNKNOWN for that shard; do not fabricate attribution.

## Access-kind / width metadata hardening

The binary trace may remain C16WARP1; do not change a qualified format unnecessarily.

- opcode;

Recoverable issues are sub-goals:

- target selector drift -> re-census exact function occurrence and retry;
- missing static map -> regenerate exact local map;
- one shard failure -> diagnose/retry that shard only;
- object sidecar failure -> do not block trace if raw capture is otherwise formal; scope object attribution to UNKNOWN and continue;
- transfer failure -> retry transport only.

Do not stop the whole Goal because one target is unavailable. Continue through the ordered portfolio.
