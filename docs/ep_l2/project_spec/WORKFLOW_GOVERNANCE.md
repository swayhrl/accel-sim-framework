# EP-L2 Workflow Governance

## Purpose

This file defines how long-lived research/design state is separated from transient execution state so ChatGPT and Codex do not silently drift the project goal.

## Canonical roles

```text
docs/ep_l2/project_spec/
    long-lived research charter, architecture, evidence model, roadmap, ADRs
    owner: ChatGPT/user research decisions

docs/ep_l2/chatgpt_handoff/
    current executable stage specifications / target goals
    owner: ChatGPT

docs/ep_l2/codex_handoff/
    current execution report / review entry points
    owner: Codex

docs/ep_l2/review_packs/
    independently reviewable source/test/experiment evidence
    generated by Codex, reviewed by ChatGPT

docs/ep_l2/coordination/PARALLEL_WORKBOARD.md
    shared multi-lane execution + review state
    Codex updates execution/progress/evidence; ChatGPT updates review/decision fields
```

GitHub is the authoritative long-lived coordination medium. Chat history is not the project state of record.

## Update discipline

### Project specification

Change `project_spec/` only when the research goal, architecture thesis, evidence standard, long-term roadmap, or a major design decision changes.

Do not rewrite it for ordinary experiment progress.

Major changes should add/update an ADR under `project_spec/decisions/` explaining context, decision, alternatives, evidence, and consequences.

### ChatGPT handoff

Change `chatgpt_handoff/` whenever the next executable target or acceptance criteria change.

Handoffs may point to `project_spec/` rather than restating the whole project rationale.

### Codex report / review pack

Codex must report actual execution state and exact evidence. A Codex PASS is not an independent acceptance decision.

Every stage with code/experiment output should preserve:

```text
source SHAs
config hash
trace identity
build/tests
invariants
formal vs diagnostic classification
raw-log index
SHA256SUMS
```

Large raw logs remain outside Git and are indexed by path/hash.

## Worktree isolation

Frozen/formal worktrees are read-only to other lanes. Every new experimental variable gets an isolated branch/worktree/config/result root.

Do not use one result directory from multiple writers.

Do not rebuild a source tree whose binary is serving a live formal campaign.

## Git discipline

Use scoped paths. Do not use:

```text
git add .
git add -A
```

Commit one semantic stage or evidence update at a time where practical.

## Evidence promotion

`COMPLETE_VALID` means a run itself completed and passed local invariants. It does not automatically mean accepted calibration evidence.

Cross-lane maturity uses:

```text
SPECULATIVE_PENDING_GATE
PROMOTED_VALID_CALIBRATION
INVALIDATED_BY_UPSTREAM_GATE
```

A downstream run may start speculatively from a frozen candidate, but it becomes accepted evidence only when its declared promotion dependencies pass.

## STOP boundaries

Every executable stage must define what Codex is not authorized to begin. Typical boundaries include:

```text
STOP before BASELINE_DECISION
STOP before Opportunity Study
STOP before functional RO/TVD/Unified
STOP before primary-baseline promotion
```

The long-lived roadmap does not override these STOP boundaries.

## Review principle

A review pack must be sufficient for ChatGPT to reach PASS/CONDITIONAL_PASS/FAIL from source, diff, tests, CSVs, manifests, and invariants without trusting the Codex chat summary.

## Relation to the bidirectional workflow guide

This governance file applies the project's established ChatGPT <-> Codex workflow pattern to EP-L2: GitHub handoffs are the shared state, ChatGPT owns research decisions/specification, Codex owns implementation/execution reporting, and review packs are the evidence interface.
