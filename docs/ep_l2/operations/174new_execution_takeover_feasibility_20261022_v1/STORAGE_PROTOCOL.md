# Proposed164 result storage and recovery protocol

This is a design only; no root, transfer stream, receiver, lock, manifest transaction or daemon was created. Existing TLS, C16 and E2 transactions retain their own rules and identities.

## Layout and storage choices

Proposed server-native root, subject to owner allocation: `/home/shared/huangrulin/experiment_archive/{ep_l2|dtc_l1}/<campaign>/<execution_epoch>/<attempt_uuid>/`. In174-new its SSHFS projection is `/root/share/mnt164/huangrulin/experiment_archive/...`. No such future root was created or assumed authorized. Use a separately reserved local native workspace for source/build/tmp/active output, and keep canonical execution ledger/locks on a qualified local authority filesystem. Do not put active log append, SQLite/lock registries, small-file build trees or simulator checkpoints directly on SSHFS before semantic/performance qualification.

Store closed immutable result chunks plus small provenance/index objects on164 promptly. Independent chunk compression is useful for large repetitive JSON/text; already-compressed traces/logs may gain little. Preserve raw-file hashes, sizes, sparse layout if required, numeric uid/gid/mode/mtime_ns, symlink targets and all directory records. Reject special files, escaping paths, hardlink ambiguity or unsupported metadata until a policy is explicitly chosen. Compression/archive SHA is additional to raw-member identity.

## Transaction and failure states

1. Freeze SOURCE_MANIFEST plus ordered chunks/ranges and original-to-server PATH_MAP. Transaction identity binds project, campaign, attempt UUID, source hashes, full ordered manifest hash, target root, schema and execution epoch. New result transactions are separate from existing P9 identities. Source never mutates an admitted closed member.
2. One owner-controlled archive data stream across the shared facility; reuse the qualified receiver mechanism after scope review rather than introducing a competing controller. Default inherited conservative ceiling:30 MiB/s aggregate,<=256 MiB staged payload,<=128 MiB raw chunk, with Share>=40 GiB and RAM>=64 GiB where those existing policies apply. These are ceilings, not a fresh allocation; current remaining Share headroom is only~1.15 GiB. Concurrent simulator plus compression/hash cost must also be reserved.
3. Before every write, check actual Target hostname/mount namespace, `findmnt` source/FSTYPE and target containment. A missing164 mount is HOLD: never fall back to the local mountpoint. Write unique `.partial` objects in the designated164 transaction root; close and reopen, SHA-check and validate decoder/member bounds before immutable final publication. Atomic rename/visibility is not a claim of server fsync durability. Native server close/fsync/readback receipts or an explicitly accepted storage-durability contract are needed for that stronger claim.
4. Persist every range identity/hash/length/offset and status. Resume by exact transaction ID and missing ranges only. Existing committed identical objects are verified and reused; different bytes or metadata at a claimed final path cause HOLD, never overwrite. Truncated partials remain uncommitted; a crash before durable final marker cannot count as success. Retry finite ordinary transport failures without spending a scientific attempt or restarting simulation.
5. Before scientific terminal acceptance, join expected raw-file complete SHA, gap-free nonoverlapping ordered coverage, exit/owner/progress evidence and project-specific correctness decoder. `ARCHIVE_VERIFIED` does not mean science PASS, native restore PASS or source space recovered. A bounded terminal outbox failure is ARCHIVE_PENDING, not permission to remove local data or falsely mark complete.
6. Restore by reading persistent164 objects into a fresh ABSENT native directory, no overwrite, path traversal protection and bounded resource budget. Independently verify every original byte SHA and full required file/directory metadata. Persist full evidence and a self-contained RESTORE procedure on164 and in Git. SSHFS projected ownership is not native metadata proof; use a qualified native restore filesystem and the project's approved scope. Native164-only proof specifically needs a real164 command/cooperation entry; Target tmpfs proves only the expressly approved alternate scope, never persistence.
7. Only after immutable archive/restore receipts, remote Git readback and an owner-specific explicit local-retention/reclaim policy may **new, owned, closed disposable local outputs** become RECLAIM_ELIGIBLE. Use a precise manifest, current-reader checks, persistent INTENT/DONE and per-file identity checks. Interrupted cleanup remains a reconciled pending state; failure cannot trigger broad recursive deletion. This study authorizes no cleanup. All old174 historical data stays KEEP, including previously archived assets.

Accounting fields must remain separate: raw logical bytes, compressed stored bytes, physical local allocated bytes, bridge temporary allocated bytes, NAS stored bytes, recovered file count, archive/restore verification counts and actual local free-byte delta. Hash references deduplicate storage only when identity and ownership permit; never add the same bridge/NAS mirror twice or report archiving as released Source bytes. Re-measure actual device free bytes after any future authorized reclaim and retain unexplained concurrent-write deltas.

## Performance risks and evidence limits

No throughput, latency, simulator-speed or trace-stream benchmark was authorized or run. Therefore **no claim of unchanged simulation speed is established**. The existing industrial archive receipt, freshly read as a small control file, records9 files/120 chunks,15,498,539,389 logical bytes and503,611,418 compressed bytes, with1258.16 s for that operational phase and full raw SHA verification. It explicitly says native164 restore was not executed under that task's simplified acceptance. Its repetitive JSON compression and inclusive phase timing are not a NAS bandwidth measurement, native restore proof or a predictor of trace simulation speed. Existing archive operations establish that the164 route has transferred and read back bounded data; they do not establish hot-trace throughput or native filesystem semantics for these projects.

| Route / workload | Main risk | Design response / future qualification |
|---|---|---|
| Local SSD native trace and workspace | Shared backing disk currently nearly full; same host contention | Separate reserved device/quota; account write peaks and output reserve. |
| Existing Source-private trace | No Target path/mount today | Owner-approved readonly exposure or one separately approved materialization; no guessed mapping. |
| Shared md127 trace | Rotational random/reopen latency and near40 GiB boundary | Reuse only an exact already-shared qualified input; compare real workload wall time later. |
| SSHFS trace on164 | Network/FUSE/stat latency, reconnect, cache state, seek/reopen stalls | Keep out of production hot path until paired qualification; bounded local immutable cache if separately approved. |
| Active results directly on164 | Append/rename/flock/durability/mtime semantics and network stalls can affect progress guards | Local native hot logs; offload only immutable closed members/chunks. |
| Background compression/hash | CPU/cache and disk contention on the same physical host | One bounded archive worker in later approved phase; priority/throttle and finite backpressure. Never alter other tasks. |

A literal future attempt to write most large results promptly to164 is feasible as a closed-chunk pipeline, not an unbounded accumulating queue. Require drain rate greater than average closed-output generation, and local reserve covering worst-case outage plus largest unfinished member. If no reserve or164 fails, pause new admissions via the authorized project controller; treatment of a running scientific attempt remains its existing policy, not a storage worker's unilateral kill decision.
