# Scientific impact and next-Source boundary

D01 is a confirmed avoidable frontend exclusion in Source78: ordinary non-RO requests do not reach the otherwise generic same-set RO relief path when raw Tag allocation fails. This is a functional/performance-path mismatch, not a proven data corruption or permanent deadlock. Source78 production-method/partition CPU evidence establishes a constructible trigger; existing accepted-application incidence and cycles effects remain UNKNOWN.

Old application cycles remain observations of the frozen Source78 implementation. Preserve Source/spec/raw/acceptance identities and negative results. Do not rewrite those cycles, combine a patched CPU binary with old app results, or declare all prior experiments invalid. The intended architecture's general mixed-request T capability is incompletely implemented; standalone T benefit is still unproved.

Backend production TagFAIL counts retain their stage-defined meaning. Zero at ft_access cannot exclude a full-set ordinary request rejected before access. Earlier high-associativity workloads with independently measured RESERVED peaks below all-way occupancy are not automatically affected by this finding. Current heavy-OFF REF lacks the joint event needed to quantify it. No marginal-count multiplication or assumed P1 incidence.

W_ONLY and WV without RO runtime cannot exercise this RO-release mismatch; their engineering qualification can proceed independently. RO-enabled F and F-minus-T eligibility and future T claims must account for it. T_OFF and reused/ineligible transactions remain protected in the tested candidate. Host-writeV3, Source92 P2, MSHR64 and new collectors must not be bundled silently into a correction Source.

The seven-line functional patch is a private CPU candidate, not a complete new simulator. Its diagnostic consulted/intermediate fields still need to reflect ordinary virtual relief while preserving raw probe state. Full build/TU/library identity, untested resource gates, observer NI, Host/native/input qualification and a new exact Source/ELF remain pending. A real same-ELF old-policy/new-policy control is needed to isolate the correction, and corrected F-minus-T/F to isolate T. Any application plan needs separate fresh authorization, not this engineering scope.

P2 constraints are real modeled costs: finite serialized metadata lookup and response stages, bank color and service limits, mandatory/pinned lifetimes, descriptor/per-address capacity and reuse_seen safety. They are not bugs merely because performance is negative. Metadata comparator/port/timing fidelity and service-aware retention benefits without measured pressure remain P3/UNKNOWN. Same physical S/F SRAM does not imply equal role-reachable capacity; retain the existing fixed-physical organization contract.
