# EP-L2下一阶段实验与机制优化协同Goal

**Goal ID：`EP_L2_WV_RO_T_PERFORMANCE_EXPLORATION_V1`**

**性质：** 现有 `EP_L2_FULL_WORKLOAD_PERFORMANCE_POTENTIAL_EXPLORATION_V1` 的协同扩展计划，不重启或替代正在执行的第一阶段。

## 0. 总目标与科研优先级

本阶段首要目标是**尽可能挖掘EP-L2能够实现的端到端性能优势**。

三条方向并行推进：

- **A：完整F与W/V结构参数优化。** 寻找能够提高真实性能的Payload、Writeback、Victim和上下游配置。
- **B：RO有效利用与Tag释放机会扩展。** 研究RO覆盖、接纳开销，以及普通native请求利用旧RO事务释放Tag的可行性。
- **C：更积极且安全的Detach策略。** 研究`reuse_seen`限制下，是否存在能够保留全部事务语义、却扩大可释放Tag范围的设计。

不能以RO候选数、detach次数、队列占用下降替代实际性能目标。

当前以性能空间探索为主，详细机理归因作为后续阶段。允许先做必要的正确性和资源资格验证，但避免大规模事件日志与重复诊断拖慢主实验。

## 2. 路线A：完整F与W/V结构性能优化

### A1. 模式组织

优先支持以下正式实验模式：

| 模式 | 用途 |
|---|---|
| S | 正式静态基线 |
| W-only | 隔离In-place Writeback效果 |
| W+V | 当前重点优化的W/V组合 |
| F−T | W/V/M开启，T关闭 |
| F | W/V/T/M全部开启 |

`W+V`可复用现有`WV_ZERO_RO`语义范围。

W-only若当前生产Core没有完整合法开关，应先独立工程实现和验收，不把旧版本W-only结果直接拼接到新矩阵。

V如果依赖W、统一池或WAD基础，则不强制构造不合法的V-only模式；优先比较W与W+V。

F−T/F仅在RO资格满足时进行同背景的T独立比较。

### A2. 参数优先级

优先探索：

1. **Writeback：** WBUF/WAD资源、写回保留与in-place服务、静态WB资源划分及实际bank争用。
2. **Victim：** clean-victim保留容量、保留策略、回收策略、fixed victim分区与动态共享池。
3. **Payload：** 统一1168个物理slot的角色使用、同bank颜色约束、动态分配和保留代价。
4. **bank服务：** 已有P1与独立Source92/P2的真实能力及成本，不把P2当免费带宽翻倍。
5. **上下游联合：** L1/L2 Miss Queue、Line-MSHR、descriptor、Lower FIFO、FR-FCFS、DRAM服务能力与组合。

所有参数应以生产源码确实支持的范围为准。需要新增策略时，先独立CPU验证，再纳入匹配实验。

保持公平资源预算，并增加合理调优的强静态S对照，例如经过资格认证的静态WB64配置。不得将同容量模型直接视为等面积证明。

### A3. 搜索顺序

先利用已接受结果和低成本统计筛选候选参数族，重点参考GEMM、FWT、Conv、Vector等已有正负证据，同时保留BlackScholes、ATAX、SGEMM等独立负对照。

接着在覆盖不同访存特征的开发集合上，对W-only、W+V、F作较宽范围参数搜索。

选择有效组合后，在完整科学合格主工作负载集合进行验证，不以少量正结果代替全体结论。

现有35冻结代表输入、42程序身份收敛、96 ordinary内容组扩展继续推进。已有完整S/F不重复启动，W/V新增实验按真实身份和资源需求登记。

结果同时报告绝对cycles、同配置相对S收益，以及同等成本下传统结构可以达到的性能。

## 3. 路线B：RO覆盖和实际利用优化

### B1. 保留现有RO判定为可信参考

现有RO资格为：

- 完整commandlist/epoch范围内的128B line只读认证；
- ordinary `GLOBAL_ACC_R`，非write、非atomic、非内部RO packet；
- Source、manifest、ranges、真实loader和完整epoch符合当前合同。

任何新的分类方法都不得放松已有正确性假设来虚构覆盖。

优先批量复用现有证书、Source资格和已冻结输入，不重新全盘读取巨大Trace。

### B2. 扩大覆盖的两个候选

**候选RO-C1：软件或运行时显式不可变区域。**

研究可以由程序语义证明的只读buffer。验证地址范围、完整生命周期、host/device写入和别名约束。需要时使用有限表项或元数据，显式承担查询与控制成本。

**候选RO-C2：有限阶段只读epoch。**

对于先写入、同步、随后只读的数据，探索是否能在已证明的阶段边界进行RO认证。

这一方案涉及epoch关闭、待完成写回、host更新和地址身份变化，不能仅根据每个kernel里没有store就认定安全。

上述方案先进行CPU-only适用性研究。现有whole-commandlist oracle继续作为参考，不将oracle上界冒充已经实现的硬件分类器。

### B3. Native请求利用旧RO Tag

当前代码的一个候选优化是：当新请求不是RO，但目标Set全部Way处于不可替换RESERVED状态时，允许其检查是否存在**旧的、合法可detach的RO事务**。

研究目标是使更多正常请求能够利用T释放的Tag，而不仅限于新请求本身也是RO。

候选实现要求：

- Preview只读判断，不直接修改Tag或事务。
- 实际commit前重新验证候选Tag、Payload、generation与全部资源。
- 确保旧RO事务、sector、waiter和下行返回责任不丢失。
- 不允许native write或atomic绕开认证范围和同地址冲突保护。
- 不新增未计入预算的地址CAM、Tag查询端口、数据缓存或descriptor池。
- 候选无法安全提交时，保持旧状态并正常背压。

工程验证至少覆盖新native请求、已有RO返回、Tag复用、同地址再次访问、WAD/dirty victim、sector乱序和响应背压。

通过CPU正确性后，建立`F-original`与`F-native-relief`的同Source、同输入、同硬件正式配对。

## 4. 路线C：Merge-aware Detach策略

### C1. 研究对象

当前`reuse_seen`一旦被RO merge置位，就持续禁止该事务detach。

这一限制可能减少可释放Tag数量，但它属于已经实现的保护协议，不能直接删除或清零。

子Agent首先构造并验证一套保留全部旧等待者的候选策略。

研究重点：

- 合并过的RO事务，其所有旧等待者是否仍能由独立事务身份完成。
- Detach后同地址新请求的处理是否正确。
- 迟到sector不会污染新Tag或新Payload generation。
- 新旧事务重复读、共享descriptor和lower队列容量是否得到限制。
- Dirty/write/atomic、host更新和非认证请求是否仍然受到原保护。

### C2. 候选模式

建议至少保留：

- **T0：** 当前严格`reuse_seen`策略。
- **T1：** 经CPU验证的Merge-aware Detach候选。
- **T2：** 若路线B的native-relief独立正确，再研究两项优化联合启用。

T1必须作为可关闭的独立策略。只有证明确实需要新数据结构时才能增加，并记录面积、容量和时序代价。

优先用CPU测试及少量真实应用pilot判断是否值得继续，而不是先构建大型复杂控制器。

### C3. 性能实验

初始参考：

- Conv：已发现真实满路NEW及RO历史正资格。
- Vector 32×4：已观测27次实际detach，但T独立收益尚未验证。
- 新一轮S/F结果中具有RO正资格和真实事务压力的其他输入。

先验证合法策略与应用终态，再比较完整cycles。若真实负载中策略没有扩大有效接纳机会，记录负结果并降低该候选的计算资源优先级；如果产生明显性能优势，则扩大到独立输入与全合格主集。

## 5. 参数组合与实验覆盖原则

所有路线共同采用两层性能评价：

**第一层：参数优化。**

比较同输入、同资源条件下的S、W、W+V、F以及必要的T候选。允许多参数组合，寻找绝对性能与EP相对优势的共同Pareto前沿。

**第二层：全工作负载验证。**

一旦选出有意义的全局候选配置，在完整科学合格主集合验证，包含正收益、零收益和减速程序。保留独立holdout，禁止按结果挑选有利工作负载后再报告总体GM。

最终明确区分：

- 完整F的最优统一配置；
- W/V子方案的最优统一配置；
- 新RO/T策略的增量；
- 每个程序分别调优得到的探索性性能上界；
- 与合理调优传统Baseline的成本和性能对比。

## 6. 性能目标与EP-friendly分类

每个输入维护统一分析行，至少包含：

- 精确程序、输入、Source和配置身份；
- 已有低成本访存及资源压力统计；
- S、W、W+V、F、F−T及相关策略的有效cycles；
- 每种参数改变带来的绝对性能变化与S/F差值；
- RO资格、RO实际采用、T动作的适用范围；
- 模型资源及已验证的硬件成本；
- 所属开发集、独立验证集或HOLD集合。

EP-friendly不根据程序名称、单次正收益或detach计数直接判定。先寻找跨配置、跨独立输入重复出现的适用特征，再在剩余合格工作负载上验证。

## 7. 工程效率与动态并行

延续当前Main动态并发调度，不恢复原两个模型并发的旧限制。

优先提高**每单位主机时间完成的有效科学仿真量**：

- 利用真实RSS/PSS、cgroup、CPU及IO情况动态调整并发。
- 长任务尽早进入队列，短任务填充剩余资源。
- 复用真164输入、已接受SHA、Source和归档证据，不重复全量读取。
- 对新增Source仅做其受影响范围所需的CPU与应用资格。
- 已接受的正式模式与输入身份不变时复用结果。
- 容量不足、重复格式化输出和陈旧资源承诺按实际原因修复。
- 科学启动采用Main单一入口，预算按批次精确登记；不设置任意总仿真次数上限，但不允许无登记启动、退款或静默重试。

默认关闭重型事件Observer。只有明确需要定位高价值性能差异时才进行有界观察，不以机理分析阻塞性能搜索。

## 8. 分阶段交付

**阶段I：与当前全工作负载实验并行。**

完成A/B/C的独立工程准备、mode审查、CPU测试、参数表和候选配置。现有第一阶段科学运行不受干预。

**阶段II：少量多样化pilot。**

在Source和协议资格完成后，利用独立新cohort测量W/V参数、RO native-relief及T Merge-aware候选。开发集包含有压力、低压力和独立负对照，不只选择已经加速的程序。

**阶段III：完整集合验证。**

在第一阶段结果和用户审查意见明确后，选择有性能潜力的参数和机制候选，扩展到完整科学合格工作负载。比较统一配置的完整F、优化W/V、优化RO/T及合理调优Baseline。

**阶段IV：论文机理与硬件成本。**

得到真正有效的结构后，再集中分析事件时序、资源竞争、消融、SRAM与控制逻辑面积、时序和能耗。

阶段I结束不是暂停其他Agent工程工作的要求；阶段II未产生收益，也不自动关闭全部研究方向。
