# OPTIONAL128 ownership and progress boundary

This is one private Source78 descendant. The sole producer remains the serialized memory-sub-partition frontend head; RO is rejected. No autonomous background extension writer or second address CAM exists.

- Base address creation is only commit_install or commit_dirty_promotion. Both check the64-bit creation epoch before publishing a new owner. Base completion changes state of an existing owner. A Base-negative snapshot must still match at Ext query and before Native consumption; change causes paid Base replay.
- Ext creation is only the paired clean cascade: a selected reclaimable Base CLEAN owner moves with the same Payload handle to one indexed RR Ext row, while the incoming native clean victim enters Base. Both row generations/revisions/readers and both metadata write lanes are checked before the externally indivisible commit. Ext never owns mandatory WB; WB_COMPLETE is not spilled.
- Base remains128 rows and can retain CLEAN. Ext adds128 rows, not a replacement home for the same128 clean entries. The CPU positive fills257 distinct Native lines and verifies256 directory owners plus one resident, with distinct clean symbolic sector labels.
- Ext write, atomic, or missing-sector access first pays query, waits out readers, takes the Ext write lane, invalidates/releases its own clean copy, and caches a paid negative with an invalid ticket sentinel. It then uses Native. The initial55bd failure retained a dead row token, which monopolized the finite indexed read view and blocked a different RR row; the exact fix clears that token, not the epoch proof or port rule.
- Native Tag-hit writes do not perform a hidden functional Ext lookup. All creation paths preserve uniqueness. Base promotion originates from a Base-positive lookup and cannot alias Ext. Initial Host prefill is allowed while Ext has never been populated; later Host prefill is refused before any mutation. Runtime L2 flush, RO, fixed/ideal modes and Tag populations above512 are not qualified.
- A landing-pressure Base reclaim uses the same paid two-cycle bank-compatible reduction and actual Base write lane. Its revision is discarded after reclaim, so the next head attempt reacquires the install selector. With at most512 resident tags, resident<=128 per Bank and Ext<=128 per Bank cannot alone fill292 physical slots/Bank. No reclaimable Base at a full Bank implies finite mandatory/pinned work; its independent completion remains live.
- New mode1/2 busy includes actual ft_drained so WB already owned in the cache missqueue/metadata producer continues ticking before memport tracker insertion. Mode0 retains the original scheduling behavior. Cached no-reservation selector/reclaim snapshots are not autonomous inflight work.
- The extra indexed Ext row read view admits one row/tick, at most two same-row/same-UID fanouts. Ext RCW write lane merges only BEGIN+END or BEGIN+CANCEL for one exact lease and at most two ops. Different rows or install/drop mixing backpressure. Physical grants/cycles are never refunded.
- Additional tests cover different-RR-row write/atomic/missing-sector progress, reader pins, ICNT-full response deferral, bank-denied lease retirement, epoch overflow before publication, Bank292 mandatory progress, and internal-WB-before-tracker drain. These are CPU protocol tests with symbolic labels, not a full numerical application oracle or physical timing/PPA proof.
