### Agent A：中等Tag容量与组织优化

#### 研究目标

现有G64×16提供FWT约4.94%的WV绝对cycles改善，但Tag容量增加4倍，且S同样明显受益。

需要寻找更合理的Tag组织与容量折中。

#### 首选两种结构

- G32×16：512 Tag entries/slice。
- G64×8：512 Tag entries/slice。

它们的Tag总项数均为REF32×8的2倍、G64×16的一半，但Set数及相联度不同。

固定：

- 原Source78 Core/ELF；
- DRAM850MHz；
- dram_latency100；
- 原Payload总容量1168/slice；
- 物理Bank资源；
- 原FR-FCFS128；
- 原MissQ、MSHR、WAD、Descriptor、NoC及其他参数。

实际配置合法性必须由Core生产路径确认，不能仅通过512项计数推断Bank映射和访问语义合法。

#### 首批精确实验候选

| Workload | G32×16 S/WV | G64×8 S/WV |
|---|---|---|
| FWT | 2点 | 2点 |
| GEMM | 2点 | 2点 |

总计8个新应用点。

优先验证4个FWT点，再执行GEMM。

比较以下性能：

1. 每个模式相对自身REF850的绝对改善。
2. 同一新几何下S/WV加速比。
3. 相对G64×16的性能损失。
4. Tag项数、组织方式及比较/访问硬件成本。
5. 每程序最优结构与统一结构的性能。

不能将Tag容量增加造成的普通缓存性能提升直接称为EP独有收益。

特别关注：

**512项Tag能否用明显更低的资源成本，获得G64×16的大部分绝对性能改善？**

如果两种512项结构结果不同，应优先继续探索Set/Way组织，而不是单纯增加Tag总数量。

交付：

`MID_TAG_GEOMETRY_QUALIFICATION_V1`

`MID_TAG_MATCHED_PERFORMANCE_FAMILY_V1`

### Agent B：Vector高频下的W/V/RO机制消融

#### 研究目标

修复版Vector在1700MHz下：

- S：45974cycles；
- F：55925cycles。

完整F相对S慢21.64%，并且F从1275到1700MHz几乎不再改善。

现有完整F观测包括：

- RO查询等待观察1000000次；
- Victim目录查询等待观察375000次；
- Victim实际读响应0；
- MissQ满等待观察降为0。

这说明继续提高DRAM频率不是最有效的下一步。

#### 首批实验

在**同一个已经验收的跨时钟修复Source**下增加：

- Vector4M W_ONLY，1700MHz；
- Vector4M WV_ZERO_RO，1700MHz。

新Source：

`862376f62ab19f9a677abe31c6a422028b44fcd0`

新ELF SHA256：

`083aa0d72173e8f27b298a76b88898bf117f44d119379b3e3ef9edd1b7ffa52b`

利用同Source已接受的S/F1700，形成：

`S → W_ONLY → WV_ZERO_RO → F`

注意：

- S→W测量完整W组织包；
- W→WV测量V机制包；
- WV→F测量RO/M/T等新增路径及其交互；
- 不能把WV→F全部归为T成本；
- 不能将旧Source78结果混入新Source比较。

W/WV必须先完成新Source下的真实Mode、Host、Native、应用资格确认。

若已有Observer缺口影响结果可信度，应提出明确的最小NI资格申请，不得默认继承Source78的应用NI。

#### 后续实验方向

根据真实结果选择：

- 如果W、WV接近S而F明显慢：优先研究RO路径、MSHR bypass及实际查询开销。
- 如果W接近S、WV明显慢：优先研究无效Victim查询与目录服务成本。
- 如果W已明显慢于S：优先检查W资源组织、下层写回与跨时钟完成成本。
- 如果WV与F差异有限：重新评估高频平台期的主要来源。

如需考察频率响应，可另拟850MHz W/WV精确配对，保持新Source一致。

允许设计少量有成本约束的机制消融或改进候选，但不通过删除真实查询周期、免费增加目录端口或理想化服务来制造可实现性能收益。

交付：

`VECTOR_HIGHCLOCK_MODE_DECOMPOSITION_V1`

`VECTOR_F_PERFORMANCE_COST_CANDIDATES`

`NEXT_MINIMUM_VECTOR_EXPERIMENTS`

### Agent C：Victim保留容量及动态策略探索

#### 研究目标

现有实验证明：

- FWT主要从DIRTY-only保留中获益；
- GEMM依赖CLEAN保留；
- CLEAN+DIRTY整体仍是两者中的最佳结果。

因此，下一步不应简单选择统一保留Clean或统一保留Dirty。

重点探索：

**如何根据可用资源与实际请求行为，提高Victim资源的有效服务能力，减少无价值保留对Mandatory事务的挤占。**

#### 已有工程候选

独立CLEAN配额Core：

`bf4e48447136b990bd2db15e2972a4394e37d21f`

目前仅有工程CPU、构建和部分Source资格，尚无完整应用接受。

保留已实现配额：

`0 / 32 / 64 / 96 / 128`

首先核查：

- 128是否严格复现新Source默认行为；
- 0是否保持合法的Dirty-only语义；
- CLEAN配额是否只作用于允许的WV/RO配置；
- mandatory WB及WAD/sector/generation/readers保护是否保持；
- 配额控制是否有真实硬件状态及比较成本；
- 是否改变Bank/Payload有效容量和前进性。

#### 建议第一批性能候选

在独立配额Source下，针对FWT和GEMM准备：

- 默认CLEAN cap128；
- 中间CLEAN cap64；
- CLEAN cap0。

共6个WV性能候选。

它们必须使用**同一个配额Source/ELF**，不能直接以旧Source78 WV作为新的正式OFF参考。

后续再根据结果考虑cap32、cap96，或压力感知配额。

此外，可以并行研究：

- Dirty-install跨CLEAN/WB_COMPLETE event-age回收；
- 每Bank颜色的可选保留空间；
- Optional Victim与mandatory WB的有限资源优先级；
- 结合真实保留和访问情况的动态配额。

但每个新机制应独立开关，先经过CPU正确性验证，不一次性合入多个机制而失去因果对照。

本轮重点是尽快形成可运行候选，而不是继续制作长篇机制分析。
