# 下一批最短必要流程

本表是文档建议，不是执行授权；参数以当次冻结manifest和主Lane实际准入为准。

| 情形 | 复用 | 新增必要工作 | 不要重复或混淆 |
|---|---|---|---|
| 同输入修observer | 已接受binary/argv/input QA与未变map/保护母件 | 新SO/MF/import/相关ABI反例→单GPU新run→相关数据闭合 | 不重跑原201launch QA，不修改旧失败 |
| 完整source待归档 | 已接受records/CRC/SHA Root证明 | 精确计划→COPY receiver SHA/COMMIT→typed登记 | 不重新解压全record，不冒普通7 |
| repeat100→2新ELF | 原source/device image证据、原QA方法 | 新身份/loop-loss→新QA→必要实际launch/输入→支持此profile的collector | 不把预期5launch当实测，不完成旧7profiles |
| parent-derived | 已接受裁剪样本和协议 | 父真实COMMIT后绑子，public CAS和读取 | 不预测parent SHA，不重复父输入正文 |
| 新metadata schema | 原执行/Budget/SHA/父链算法 | exact ID/schema/用途窄兼容；新对象installed inspect与对应旧格式回归 | 不默认全156 O(n²)长计划或全库正文恢复 |
| 新ISA/TEX/mask | 原QA、source/actual loaded与保护链 | 代表profile动态证据→接受→全记录→风险完整CTA→按实际条件推广 | 静态编译不等支持，不要求所有潜在分支 |
| 模型耗预算 | 已校验trace/原样本 | UNKNOWN_BUDGET；判清预算与真实不兼容后调整确切试验 | 不自动改科学预算，不写workload unavailable |

提交前五问：

1. 新闭合哪个缺口，属于原输入还是新profile？原状态是否被新版本掩盖？
2. 复用哪些已接受且bytes未变证据？重做是否仅出于习惯？
3. 最早真实拒绝在哪层：QA、ABI、collector、格式、POST、归档、发现或consumer？
4. 完整CTA覆盖/未覆盖什么？正常退出和source+aux退休一致吗？
5. 源/实际父链/receiver COMMIT/请求id/owned关闭及方法证据，其他项目是否可读取？

取舍原则：删多余环节不删必要字段与完整性。新格式必须先明确字段/缺失/变换及信息损失，不能“填零让它过”。详见METHOD_V2.md、PITFALLS_V1.json、EXECUTION_CHECKLIST_V1.json。
