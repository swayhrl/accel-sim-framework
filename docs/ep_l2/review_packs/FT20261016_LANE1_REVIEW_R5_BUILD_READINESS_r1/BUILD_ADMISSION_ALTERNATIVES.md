## 48GiB的必要性：已知与未知

Lane5 初始 HOST_BUDGET 将48GiB定义为保守运营保护值，初始空闲63.74GiB；r5再次明确它不是 GPU 模拟器的物理固有需求。现有证据没有建立“编译器本身必需48GiB”的结论，也没有建立“36GiB足以安全构建”的结论。它保护共享磁盘、并发研究、构建/输出增长及停止后的余量；需要根据实际高水位和其它项目写入边界审查，不能只比较最终可执行文件大小。

历史占用来自自己的 R0/R1 build 目录，以及上一轮已冻结的逐文件 cache 审计（不是本轮删除）：

| build | 保留文件分配字节之和 | r3已审计移除的可重建cache分配 | 重建的清理前静态分配 |
|---|---:|---:|---:|
| R0 | 229,388,288 | 533,073,920 | 762,462,208（0.710GiB） |
| R1 | 522,452,992 | 559,091,712 | 1,081,544,704（1.007GiB） |

这些是有界文件元数据之和，排除目录块，不是历史峰值曲线或独立物理容量测量。旧 R0/R1 主二进制分别75,771,168/76,453,792B。上一轮实际 df 回收1,091,817,472B已经发生，本轮回收0B，不能再次计入。两个旧 build 目前 `.o/.a` 残留均为0；剩余 executable、原始结果和唯一证据均保留。

**仍未知**：R0.1新目标的编译临时文件与链接输出同时存活峰值、`/tmp`和构建树的组合峰值、toolchain/调试信息波动、失败重试残留、同盘其它进程的增长上界、磁盘检查到自己进程组停止的最大写入量。两个新增测试意味着旧目录静态总量也不是新构建的保证。现有2GiB增长预留是冻结的保护政策，不是本轮已测得的峰值。多次离散 df 读数只能显示空间变化，不能将全部变化归因给 DTC-L1，也不能推出它未来的最大写入率。

## 可供审查的方案（均未自动执行）

| 方案 | 能解决什么 | 证据缺口 / 审查条件 | 本轮决定 |
|---|---|---|---|
| A. 保留现行准入，由现有 Storage-Ops 恢复空间 | 保持统一 build/应用保护；不引入新二进制环境 | 源实际释放且Lane5独立复测；仅stage/归档不算回收。S01+S02约0.765GiB，即使全部实际释放，也不足本快照约14.00GiB的build缺口 | 当前采用的唯一执行政策；无重复尝试 |
| B. 根据实测峰值提出动态空间准入 | 有机会说明48GiB是否过度保守 | 先在**现行准入合格时**观测唯一正式构建（不为画像另开重复build），记录同盘build/tmp/log和整盘高水位、其它项目owner认可的写入预算、停止延迟和余量；由Lane5独立复核。若要在不足现行门槛时做试验，必须另经用户明确批准 | 仅设计，没有降低floor或启动画像build |
| C. 同机独立文件系统构建 | 可隔离对象/链接的空间增长 | 当前 `/root/share`自身也不足floor；需要证实足够free、owner配额、临时目录归属、持久性/原子发布、工具链和binary身份。中央registry仍检查workspace，迁移build并不会自动解锁正式应用 | 当前无合格本地盘；未迁移 |
| D. 其它机器或164目标 | 有机会获得独立空间 | 需实测目标空间与负载、Lane5中央唯一owner/配额、可复现工具链/ABI/CUDA依赖、完整source/config/binary身份、发布与返回读取；164归档接收许可不等于编译盘许可。必须用户同意换机/路径 | 未连接、未构建、未使用164 |

方案B的候选评估形式是 `所需空闲 = 其它项目保留空间 + 实测构建峰值上界 + 输出增长上界 + 停止延迟与未知项余量`。现在每项上界尚不完整，不能填入猜测数字，也不能据旧二进制大小推导新floor。即使未来批准B/C/D，正式应用48GiB、RAM/并发/scan限制、科学资格与run-key必须另行保留或明确裁决，不能隐式继承一次build例外。
