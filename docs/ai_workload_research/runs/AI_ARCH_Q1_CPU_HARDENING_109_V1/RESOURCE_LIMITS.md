本表读取固定V1/R1证据及候选源码。早期峰值不能外推为晚期峰值，不能把未观测超限等同于完整资源观测PASS。

## 用户已批准但会影响恢复组织的边界

- 只有一个非阻塞持锁窗口。资源冲突不能等待重试；窗口一旦释放，剩余时间不能用于第二次取锁。这是两轮工程错误后不能原地继续的直接组织限制，不是算力或容量不足。
- 实际CPU集合为非独占8–21，只有14logical、约10个拓扑core；T16是OMP线程cap，不代表16个物理核。用户允许最多16训练logical不等于当前已有16可用，不能自行侵占预留0–7或监督22–23。
- 不改变算法、pending梯度、densification和质量合同，不能用削减真实训练工作绕过内存/时间限制。
- 身份、门控、未知GPU任务和可信观测失败必须STOP。本次R1恰是异常worker退出时未满足该条件，不是容量cap触发。

## 代码中额外的保守条件：本次没有静默放宽

| 代码条件 | 实际作用 | 性质 |
|---|---|---|
| 启动前MemAvailable≥50GiB | 节点总主存约62GiB，即便任务不需48GiB，也可能因其它合法占用而拒绝准入 | 实现保守条件，用户没有直接指定50 |
| 启动前free≥96GiB | 64GiB新增预算+32GiB保留按最坏情况预留 | 实现保守条件 |
| 运行中MemAvailable≥10GiB | 保护节点主存余量 | 额外安全阈值 |
| 自身观测VmSwap≤64MiB | 防止换页/主存压力 | 额外安全阈值；代码比较当前小计，并非已校准的增长量 |
| 新job至少预留600秒 | 持锁超过2h50m后不再启动新job | 实现调度余量，不是用户另设总次数限制 |
| held到10800−120秒退出 | 约2h58m开始清理 | 资源安全预留 |
| Goal到28800−25秒退出 | 仅留25秒归档余量，完整push/API回读耗时可能更多 | 实现余量，不能保证压线时完成Git归档 |
| checkpoint raw storage单份≤28GiB | 实际store.save/load保护边界，低于主存48GiB不代表恢复总峰值≤48 | 实现上限 |
| Torch allocator fraction=13/16 | RTX4080上Torch allocator约13GiB，低于NVML14GiB；外部分配另计 | 实现保守限制 |
| disk_bytes(root)≤64GiB | 统计整个执行worktree的逻辑字节，包括继承文件，不是严格的私有新增磁盘 | 保守统计口径，应明确记录，不能冒称精确私有增量 |
| 共享桌面显存/activity与Image-Lab门控 | 只有已验收resident和桌面可共存，无未知compute | 继承共享资源策略，不是可忽略的性能噪声 |

上述条件可比用户容量上限更早停止任务；本次没有证据表明其中任一阈值实际造成R1停止。改变它们需要形成明确的新执行策略，不能暗中改大预算或跳过安全监控。

## 完整晚期状态可能成为真正限制的地方

1. 保存同时保留C_D、C_V和输出/滚动state时，需要累计磁盘预算。若每份为S GiB，三份加cache与日志应满足3S+其它新增≤64GiB；约21GiB/份以上就可能装不下三份。这是条件估算，不是已测checkpoint大小。不能靠先删C_D制造成功。可在同一科学合同内规划保留必要canonical、减少冗余临时副本，但必须先保存验真再安全轮换。
2. 单份28GiB实现上限、40GiB sampled RSS和48GiB charged是三个不同合同。恢复加载、原runner临时state、optimizer与pinned-buffer若同时存在，可能先触及任一项。早期1.66GB state不足以确定晚期需求。
3. 真正自然推进到晚期所需GPU持锁时间尚未由本轮测完。三小时能否覆盖生产、恢复、正式对照与drain未知；目前不能据此申请扩额，也不能承诺一定够。
4. 当前cgroup memory.max=max，是root-owned SSH session的只读聚合观测，不是48GiB内核硬隔离。1秒采样无法声称不超瞬时峰值；kernel memory.peak补充已退出子进程charged峰值，CPU helper会话范围另列。

结论：现在先修工程，不建议凭这两次失败提高资源上限。未来真实晚期数据若证明某项不足，再只针对测得缺口申请。当前CPU只读快照见raw/CURRENT_CPU_RESOURCE_SNAPSHOT.json；它不是GPU窗口授权或未来资源空闲承诺。
