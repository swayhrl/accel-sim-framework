# AI负载体系结构研究：跨项目协调规则 V1

## 1. 科学权威分层

1. **执行与科学结果**：各项目自己的exact commit/tree、输入、代码、raw及SHA、实验合同和独立审查。历史结论保持不变。
2. **共同知识层**：本分支的问题图谱、证据索引、论文实验组、研究问题/机会清单。它负责导航与对照，不替代第1层。
3. **新实验授权**：由用户与负责项目的ChatGPT窗口单独确定。协调分支记录候选，不产生自动Goal。

## 2. 分支边界

- 协调长期分支：`hrl/ai-workload-research-coordination`；仅作研究资料更新。
- C16实验分支：保持原commit/branch和Stage A冻结，不因本分支建立而重开。
- AWMA执行/文献分支：保持原有Lane及合同，尤其R27R3或未来新Goal不受本分支变更影响。
- 以后确有跨项目共用代码需求时，先分离可复用工具与科学输入/语义，再单独审查移植；**禁止通过合并两个历史实验HEAD来产生“总执行分支”**。

## 3. 新证据写入条件

- 每个事实要包含：`model/input/workload`、阶段、GPU/部署、实现/precision、变更变量、强软件对照、原始指标及单位、实验范围、fixed source commit、证据类别、不能外推的范围。
- 明确区分Native、模拟器、源码、作者论文、独立重算、设计假说。
- 实验的机械执行PASS不等于科学问题成立；STOP不等于现象不存在；已有负结果只对对应冻结条件成立。
- 文献按`论文版本×具体实验组×workload×配置×对照×指标`归档；作者原话与我们的推论分开，未披露不补造。
- 新版本可以增加`V2`文件或小范围维护索引，但不能无说明覆盖历史snapshot或重解释acceptance。

## 4. 新研究问题路径

**发现层**：从文献或原生数据提出可证伪问题；允许小预算、强对照、预冻结STOP的发现性probe，即使完整oracle暂不可得。

**定位层**：明确合法测量边界、成熟软件基线、局部与整段/容量上限、竞争解释及最近邻。

**机制层**：已有明确未解决约束时再投入模拟器/硬件设计；保留零/负结果、资源开销、独立验证。

不得用逻辑重复请求数等价于DRAM请求数、stall时间或性能收益；不得以本地kernel加速替代整请求加速。容量、时间、质量、收敛与功耗分开。

## 5. 跨窗口同步工作流

1. 两个项目在启动新研究设计前，按需只读fetch本协调分支`README.md`、图谱和证据索引。
2. 如发现新现象，项目仍先完成自己的独立科研审查，并固定`commit/tree`与原始证据。
3. 研究协调窗口把跨项目相关结论追加至索引，并更新`CURRENT_STATE.md`的指针；未独立审查的结果标记为`REPORTED_PENDING_REVIEW`。
4. 新科学问题可以在任一项目被发现；属于哪个项目与是否进入GPU，取决于冻结的科学对象和资源，不由目录名决定。
5. 同一GPU继续使用既有campaign lock；174/109/164职责不变，协调分支更新本身不获得节点操作许可。

## 6. 更新与审计

- 文档更新以小型可追溯commit发布；保留旧文件、旧commit的明确引用。
- GitHub固定commit链接用来保证研究笔记可以长期追溯；`CURRENT_STATE.md`是导航快照，不宣称实时监测远端任务。
- 若AWMA/C16各自状态更新，协调分支允许短暂滞后，但严禁用旧导航快照覆盖新项目authority；发生冲突时，以对应项目已接受的最新独立审查为准。
- 只有研究方向调整或跨项目实质新证据，才需要更新图谱；避免每次小型runner工程修复都触发管理型Goal。

## 9. 依赖包装与科学输入缺失分层（A8轮经验）

- 当固定依赖版本的官方wheel缺失时，先核对**官方同版本sdist、固定SHA256、旧版本锁、预冻结wheel-only策略及其它包的完整获取门**。这一现象属于`PACKAGING_ARTIFACT_GAP`，不是自然scientific payload缺失、GPU数值失败或负性能结果；不要把缺失的wheel视为“这个版本不可安装”的证明。
- 如科学合同**已经规定缺wheel即STOP**，先保留合法终态与全部raw/receipt，不能自行切换源码安装或把失败的执行继续成PASS。只有经用户明确授权的最小后续合同（例如仅**原版本、原hash官方sdist**的一次有界CPU构建）才可恢复；由新wheel产生的新hash需另列派生来源，不覆盖原sdist或版本锁。
- 此类门应尽量在大型依赖下载、JIT和GPU锁之前，以CPU侧只读发行元数据＋精确hash/可用性检查筛出；严格区分第一次失败和全部依赖已通过检查，避免更正一个叶包后立刻出现下一个相同STOP。
- 冻结的模型/输入/数值、原source/原GPU预算、独立分支和STOP仍是权威。只有工程包装的小且确定性的重建可以在获准范围内solve-and-continue；实质科学输入、模型语义或后端身份变化必须重新评审。

## 10. 硬件/系统API版本门：禁止用最新文档的符号充当旧环境权威（A16经验）

- 对需要被Codex**严格执行的命名API**，科学Goal在冻结前必须同时核三层：①**原目标Toolkit/SDK版本的官方文档和头文件声明/ABI**，②目标driver/runtime中该符号是否实际可解析（可先只读检测，若需API调用遵守原共享GPU锁），③该函数的**行为契约是否足以证明科学观测量**。只查最新官方文档、只找到相关概念或只在别的设备运行成功，都不等于三个条件通过。
- 严格区分`function_call_return`与输出查询状态、函数指针、返回handle的合法性，不能把调用`cuGetProcAddress`返回`CUDA_SUCCESS`等同目标symbol有效，也不能把物理SM count/普通context视为实际Green分区已创建。
- 如果Goal自己的必要API对原冻结版本不存在，**按原Goal先合法STOP**、保留receipt并将其归类为`GOAL_INTERFACE_DESIGN_DEFECT`；这不同于设备否决、模型数值失败或工作负载没有瓶颈。新的文档化API链只能在一个明确审批的最小修订合同中执行，**不能未经授权地换ABI或放大硬件探针**。
- 研究型接口实验的科学证据至少区分：源文档`SOURCE_ONLY`、实际设备API创建`DEVICE_CREATED`、context/stream拥有权与真实配额`STREAM_BOUND_QUOTA`、应用全部GPU操作确实运行于所控流`FRAMEWORK_INTEROP`、原生数值`MODEL_NUMERIC`、正式性能/机制归因`PERFORMANCE`。上一门通过不得跳级证明后续门。

## 11. 工具与工程问题一次性闭环：默认有界solve-and-continue（A19纠偏）

用户明确要求：**涉及工具、执行包装、依赖和版本接口等工程问题，尽量在一条完整Goal或同一ChatGPT回合内一次性处理，减少等待与多轮确认。** 这条原则不覆盖科学合同、GPU授权、安全共享锁、数值身份的冻结约束。

1. **先确认工具入口真正可调用，而非只确认文档存在**。对版本敏感API，CPU预检核冻结headers、ABI/函数原型、Driver符号、Python/C++实际打包的能力；对科学执行资格门，预先确认确实存在一个**可运行、可观测、可复原**的验收路径。普通CLI/manifest/缓存文件由可信已接受provenance确定性重建，不升级成scientific payload缺失。
2. **同一个已批准Goal内就地解决已许可的确定性小问题**：路径错误、runner/index/manifest包装、合法依赖wheel缓存/构建方式及固定API的机械调用问题，按预批准边界诊断→最小修复→原样复验→提交收据；不要为不改变科学条件的小修补不断停下来请示。可以设置紧凑的修复次数/时长/资源预算；无法合法恢复就保存部分成果并STOP。
3. **不得用硬编码必停代替实验**：若用户批准的是逐门G1→G4验证，runner不能在上一门通过后仅因为“尚未证明下一门”就在源码层固定写死STOP，而完全不尝试一条已审核许可的、同一live进程内的验证路径。应在设计阶段区分`SOURCE_ONLY_REVIEW`和`EXECUTED_INTEROP_CANARY`，前者只能证明存在性，后者要有可执行入口、实际数据、readback、数值与可安全退出的归属/生命周期证据。实机失败或不具安全的合法运行路径时才进入相应FAIL-CLOSED终态。
4. **阶段连续交付**：在已授权预算内，将环境资格、接口查询、数值canary、限定实验和完整report/commit/readback安排在一条连续Goal。若同一ChatGPT窗口就能完成连贯只读文献、源码或审查任务，合并执行并一次更新协调状态，不因人为Round标签增加确认轮次。
5. **科学授权/安全边界永不默许越过**：模型或输入identity、dtype/容差、实际算法/强后端、硬件资源轴、完整时间分母、GPU共享锁/节点权限、下载/安装/设备预算、已STOP后的新GPU目标或新增机制，凡发生实质变化必须STOP并获得明确新许可；不得用“工程修复”绕过。
6. **节制失败重试**：已审批的一次性recovery已按合同STOP（如A16R1 G3），不自行循环R2/R3。首先独立审查**是否真正执行了目标验证，还是仅因设计/包装而未测**；如果没有新的科学价值或未形成可证明的执行路径，停止该路线，将工具能力作为有限事实归档。任何未来独立实验必须另立有价值的科学问题与审批，而非单纯“再修一次”。

## 13. 大型压缩输入的安全准入：未知展开大小不等于真实磁盘不足（A27经验）

- **拆开三个可辨识的阶段**：①下载前可验证的**压缩实体大小、权威来源/许可证、当前磁盘和网络预算**；②在压缩文件能够安全落盘后，**不提取用户数据的流式tar完整成员/尺寸与路径安全审计**；③通过后，按**实际磁盘/内存硬限额**提取及产生处理派生文件。若发布方没有体积manifest，不能错误要求阶段①凭HTTP头和gzip footer已经证明阶段②全部解压大小。
- [RFC1952](https://www.rfc-editor.org/rfc/rfc1952.html)的gzip `ISIZE`仅为未压缩长度**模2^32**；大于4GiB的tar和多member文件不能从最后4字节得到展开上界。HTTP `Content-Length`一般只是compressed字节数。不要用JPEG经验压缩比例/单个member前缀猜资源资格，也不把同源目录的`404`当作官方manifest全球不存在。
- **安全实证流程**：先审下载压缩文件本身的已知容量是否处于用户明确批准的网络+磁盘+剩余空间额度，再通过实际checksum/Range identity下载一次；使用只读tar listing/stream解析成员体积，扫描期无展开写盘，拒绝恶意path、special file、link、重复冲突、异常PAX及无法约束的解压炸弹。解压和后续resize/build/cache/checkpoint累计实时限额；共享FS空闲突然变化时按硬条件STOP。
- **这不是默认大下载授权**：若旧科学合同明确将“下载前必须有expanded size manifest”作为必要门，执行者应先合法STOP并归档。新方法需要一次有范围的修订合同批准；批准后可把source/压缩实体→合法tar scan→安全提取→依赖与数值→已授权GPU诊断合在**同一个连续Goal**，不再人为拆成一个tar-index小Goal。原下载/GPU预算和真实AI输入身份不会默默放宽。
- **科学payload vs包装**：压缩大小未知、没有公开precomputed SHA、未提供tar索引是**存储/元数据包装缺口**；是否真实缺少原始图像、COLMAP camera/point文件则属科学输入缺失，要通过权威来源和完整字节/结构/对应关系实际判断。Google Drive/其他官方站点在node直接超时但controller可取只读metadata时，不能把meta HEAD说成目标节点已下载binary；有安全中转需求要明确单独授权并计入累计流量/磁盘。
