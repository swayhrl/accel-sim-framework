## 3. Separate searchable Tag limits from physical-reference capacity

**Read-only diagnosis first; new parameter runs need separate authorization.** The accepted DH organization has64 sets x8 ways=512 searchable logical Tags and640 whole128B physical identities. Nominal searchable coverage64KiB differs from the80KiB payload-capacity model, and referenced tagless lines can retain physical identities. This structural mismatch motivates a testable question; it does not prove Tag pressure causes any observed slowdown.

First inspect existing Tag misses/evictions, repeated lower requests, allocation/reclamation and physical-lifetime evidence at explicit kernel endpoints. If the needed reason or lifetime counters are absent, request a small cycle-neutral observation change as a separate qualification task rather than treating absence as zero.

A possible new experiment would increase Tag associativity at fixed set/hash geometry and fixed640-line pool, with a separate physical-capacity factor only after the Tag result. Exact supported values and option names must come from the fixed constructor/constraints; do not silently adopt a new hash family. The whole applicable frozen suite must validate any proposed uniform architecture candidate, not only ATAX/MVT/BICG.

## 4. Distinguish admission capacity from finite completion bandwidth

**Read-only diagnosis first; changes require a new architecture/parameter Goal.** CH active common PIB256 and DH active OO PIB128 are different resources; DH's raw common PIB8 and rawDTC MSHR32 are not the active OO capacities. Finite DH service also imposes separate refill/create/inject/retire grants, collection bandwidth, wakeup limits and a return metadata edge. The shared raw ordinary L1 latency20 does not establish identical hit/completion timing.

Use existing admission-full, dependency/waiter, reference allocation and completion-service event data to decide whether an admission-capacity or a service-width experiment is justified. Event counts are not occupied cycles or critical-path time. Missing occupancy/service observations require a separately qualified observation proposal.

For a new experiment, vary one active resource at a time: for example OO PIB128 to a supported larger capacity while holding service widths fixed, or one finite-service quota while holding PIB/pool/Tag capacity and return latency fixed. Keep the finite service model rather than removing timing. Progressive sector wakeup, if considered, is a distinct semantic mechanism needing dependency/sector-correctness qualification; it is not an implicit free parameter in this Goal. Disclose waiter/generation/reference metadata, ports, arbitration and frequency assumptions.

## 5. Establish the initial-state and DRAM-observation scope

**Mostly read-only; new initial-state runs or instrumentation need separate authorization.** Summarize each fixed trace's HtoD command placement, memcpy L2 prefill policy, kernel order and explicit timed DRAM reads/writes. Repeated memcpy commands are trace facts, not timed DRAM traffic or proof that all future accesses hit. The current lazy-fetch-on-read policy can produce write misses without DRAM reads. Zero-response cases must remain in the suite and be interpreted under those actual conditions.

For DRAM-sensitive cases, reuse controller queue averages, per-controller counts and MRQ histograms where present. Queue averages sample the after-scheduler pending window in DRAM ticks; MRQ measures request construction to bank assignment in core cycles. A histogram can bound a missing mean but does not reconstruct its exact value; bank RD counters do not describe all bank activity. These are not complete L2-to-DRAM service or application critical-path measurements.

If a key claim requires a different cold/steady-state condition, an added service-time observation or a controlled cache-state sensitivity run, propose a new matched CH/DH contract with explicit initial-state semantics. Do not change memcpy/flush policy inside these48 results, add a capture, or replace frozen inputs to obtain stronger performance. Keep numerical/full-application and capture-ELF evidence gaps distinct from timing-ROI validity.
