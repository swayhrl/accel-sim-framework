# Reservation and execution release

After actual C1 PASS, exactly two fresh UUIDs are recorded in an explicitly inactive, non-executable proposal. The proposal's complete source/input/runtime/options/ROI identities are published and independently read back before C2. It cannot grant a fork and is not an executable manifest.

Only after a genuine current strict paired heavy R2 passes does the source-pinned sole BA/root write a per-point executable-release manifest under its new private evidence root. This binds the exact owner instance, source registration, proposal SHA, publication HEAD, C1 PASS SHA and complete actual R2 baseline/admission. Both pre-fork callbacks verify that release unchanged along with the exclusive kernel lock, exact source/runtime stats, current ledger and full environment. The original5-second final-R2 freshness checks remain unchanged. There is no publication delay that renews or reuses a stale admission and no extra fourth recovery opportunity.

If a gate fails, no executable release exists for that UUID. Waiting holds no production FLOCK and performs no resource polling. Three host-only failures seal both inactive reservations with0model starts. AD_Gaussian needs first AD fully accepted and its own single new R2/release. Every actual fork consumes a new slot; no replacement, refund or priorUUID reuse.
