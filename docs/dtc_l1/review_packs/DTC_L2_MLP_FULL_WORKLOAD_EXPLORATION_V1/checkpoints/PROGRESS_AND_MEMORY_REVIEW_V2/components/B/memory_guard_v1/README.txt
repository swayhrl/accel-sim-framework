Physical headroom defaults to min(host MemAvailable,cgroup raw max-current), no speculative reclaim credit. Clean-inactive credit is reported separately. Soft pause20GiB / hard target10GiB / resume30GiB with hysteresis. One resume at a time, no faster than every2s, and only when its remaining processRSS hard-limit bound plus2GiB burst margin fits above10GiB. At low headroom, preserve affordable finishable work and a single affordable escape. If no owned program can safely progress, report EXTERNAL_PRESSURE_NO_SAFE_PROGRESS; never pretend STOP has freed memory or blindly CONT all programs.

Default pause order: observed positiveRSS growth rate, predicted remaining growth, optional user priority tie, RSS. pause_priority_mode='user_first' explicitly lets program preferences override growth ordering; positive user_program_priority values mean pause earlier. This can increase allocation risk or delay memory release compared with growth-first. A recent progress estimator can supply an ETA as a soft priority only. Native production ETA adapter is currently NOT connected (eta=None), so this candidate does not claim it already recognizes short finishing real applications. Regardless of ETA, remaining growth for hard recovery uses actual RSS hard-cap minus currentRSS; group finishable retention also respects the sum of those bounds.

Fixed10GiB is a target, not an OS guarantee. Each step reports a reaction envelope:
10GiB + max(observed aggregate positiveRSS growth,observed headroom fall,configured8GiB/s floor) * (previous actual step latency +.25s period +sample age +.25s actuation allowance) +2GiB burst +1GiB error.
Soft threshold=max(20GiB,envelope); resume=max(30GiB,envelope+10GiB).8GiB/s and burst/error allowances are unproven assumptions, not measured upper bounds. Unbounded external or allocator bursts can exceed them; STOP cannot restore already consumed memory. No global swap/cgroup settings are modified.

Fault/stop semantics: no blind CONT and no closing owned paused pidfds. The parent marker DTC_L2_MLP_MEMORY_GUARD_OBJECTS_V1 retains the guard object by token, pidfds and journal. An abrupt entire-process/kernel death still requires separately qualified journal/PID-generation recovery; this candidate does not pretend file descriptors survive process death.
