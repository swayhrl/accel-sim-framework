## Concrete defects in current resource-WAIT path

1. Dispatcher lines183–184 turn an admission refusal into an exception; lines285–292 unconditionally write permanent `COHORT_TERMINAL.json` STOP. With zero starts, an ordinary first/pair resource WAIT therefore seals all AG6 work. Between arms it also seals the remaining unstarted arms, although a complete valid prefix has not failed scientifically. Policy says resource failure holds new starts and prohibits background retry/replacement; it does not make an unspent UUID a failed simulation. Hard faults during an already-started arm remain STOP, not resumable resource WAIT.
2. Removing that exception or line118's `require(not budget(points))` alone cannot repair continuation. `admissions/<point>`, `AUTHORITY_ACTIVE.json` and `AUTHORITY_RELEASE.json` use exclusive fixed names. The attempt directory and canonical `INPUT_RUNTIME_IDENTITY.json` are also created before final pre-fork checks. A zero-start refusal after preparation can leave an unconsumed directory, and a later explicit continuation will collide rather than retry just its unstarted admission. Preserve all those records; do not delete/relabel them to simulate a clean first invocation.
3. Lines238–242 consume the fixed UUID before mapping-file hash/read, `run_guarded` entry capability and actual manifest/setup validation. Pure mapping/preparation failure or a stale-sample rejection can consume a slot before an attempted fork. Actual guard lines39–54 call capability first, then validate all manifests, create evidence/fds/seccomp state, and only later call `os.fork`. Thus the current <=5-second check in capability is also earlier than the real fork boundary: subsequent work can make it stale. This is an actual call-order gap, not an invitation to refund an existing conservative `RUN_START`.
4. Repeated `publication()` calls verify whichever current publication/readback they load, but their returned manifest/head are ignored after the initial load. A changed release on disk could pass that fresh check while the running process retains the earlier imported guard and captured manifest/points. Pin the invocation's executable manifest/source/identity contract and qualification closure to its initial immutable release; a later result-publication commit may preserve exactly those blobs, but may not silently switch execution closure in an already-running process.

## Small finite continuation state machine

Use one new exclusive foreground invocation/session directory (parent-chosen unique identity, not a simulation UUID). Put admission, unconsumed preparation and authority active/release receipts under that session. Each invocation performs at most one admission pair for its next pending arm and a finite pass over the remaining fixed order. A WAIT returns after recording its immutable checkpoint and releasing only its own lock; there is no retry loop, timer service or background auto-resume.

At entry, derive the conservative consumed prefix from the original four registered `RUN_START` rows. Require exact point/order/UUID/path/source/registration joins, no duplicates or non-prefix rows, and the original cap4 unchanged. A continuation may skip a consumed row only when its immutable original strict/terminal/resource/mapping receipts are complete, accepted and source-bound, with actual roots/owned instances drained. Pin those prior receipt hashes in the checkpoint and remote publication; do not rerun or rewrite them. Any consumed failure, missing terminal, unresolved cleanup, lost/inconsistent row or committed reservation without completion seals STOP/incomplete. No inference from absent `FORK_CHILD.json` may erase a consumed reservation or enable a same-UUID second launch.

Resume only when the latest checkpoint is a pure **pre-consumption resource WAIT**, no cohort STOP exists, current exact authority is closed, the fixed science/four UUIDs/BASE eligibility/executable closure still match, and all prior consumed rows are accepted. Explicitly continue with `points[len(consumed_prefix):]`. This is continuation of unstarted experiments in the same cohort, not restarting an already-started experiment. Every next arm gets entirely new full R2 samples and own write-footprint admission. Zero-start WAIT keeps0/4; WAIT after two complete arms keeps2/4 and their exact results; neither assigns a new UUID nor repeats an arm. If four accepted rows already exist, produce the aggregate closeout without launching anything.

Resource threshold failures before consumption (IO/memory headroom/disk, or a fresh pair refusing new work) can produce `PAUSED_RESOURCE_NO_NEW_START` checkpoint/session terminal, with `next_point`, consumed prefix, attempted-admission hashes and `automatic_retry=false`. Keep the canonical `COHORT_TERMINAL` reserved for **four accepted results** or **hard scientific/identity/authority/started-runtime failure**. Wrong site/output identity, unknown authority and source/BASE/science changes must not be flattened into an ordinary resource WAIT. A signal before consumption records an explicit interrupted hold, with no implied permission to continue; an active-arm signal remains its actual consumed STOP.

Stage identity and admission receipts outside the canonical attempt directory until ready to commit consumption. Alternatively introduce per-invocation preparation records within a preserved unconsumed attempt, while writing canonical launch files exclusively only once. Never overwrite an old `INPUT_RUNTIME_IDENTITY`, admission or aborted preparation. On continuation, fresh staging must refer to the same point/UUID and immutable config/runtime, rather than treating stale preflight evidence as current.

## Conservative start / guard boundary

Prepare mapping bytes, actual manifest validation, output/fd/seccomp setup and other fallible nonlaunch work before the consumption boundary. The qualified guard needs an explicit final pre-fork hook, after that preparation and immediately before its actual `os.fork`, to recheck the fresh last sample/current capability and then write the exclusive conservative `RUN_START`/lease. No expensive publication/hash/manifest work may follow that hook before fork. The existing early capability can still establish that this is an authorized simulation target, but must not be mistaken for that late boundary. This is a necessary production interface change for parent review/targeted qualification; this review supplies no simulator canary or permission to run one.

If a refusal happens before the late commit, record prestart WAIT/failure with no conservative consumption. If the exclusive `RUN_START` has been committed and `os.fork` then fails, preserve the already-declared conservative consumption and fail-stop; never reset/refund/replace it. A crash in the commit-to-fork gap likewise remains consumed/unresolved. Count conservative reservations and actual fork children separately. Existing consumed rows must retain their original semantics, even when actual fork count is smaller.

## Terminal and release behavior

Current per-arm strict/resource/identity failure handling preserves start/terminal/failure receipts and stops new dispatch; keep that behavior for every consumed arm. A complete but slow/negative speedup is still an accepted strict result: it must neither stop nor be replaced. Current `collect` accepts on strict validity rather than a favorable speedup, which is consistent with the frozen selection rule. Build final `results` from the verified prior accepted prefix plus newly completed rows; only all four exact registered arms may yield COMPLETE or selection. Incomplete discovery remains provisional O.

Put each invocation's release receipt in a real outer finally after the local lock handle closes, including exception paths during active-record/terminal writing. Distinguish lock-not-acquired, own-lock-closed and owned-root-cleanup-unresolved; do not claim instance closure from merely releasing the FLOCK. The existing with-block closes its own lock on exceptions, but fixed-name release writes can be skipped by exceptions before/inside terminal writing and cannot serve multiple sessions. Never delete another lock, signal another project or discover/adopt roots to make a resume possible. An unresolved consumed root remains STOP and requires independently observed closure before any other dispatch; lock release alone is not that proof.

All session/checkpoint/results remain GitHub-published and hash-bound. Preserve the original executable release/source blob identities separately from later status-publication commits. A continuation must not silently change code/qualification source; any necessary source repair needs explicit scoped review and evidence transfer, rather than resetting the cohort or spending BA32/extra AG6 slots. This review is a concrete source finding/design suggestion, not executable registration or an assertion that any model was started.
