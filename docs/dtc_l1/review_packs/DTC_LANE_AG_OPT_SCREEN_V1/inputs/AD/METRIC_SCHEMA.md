# AD metric schema V1

Export occurs only with progressive wakeup ON at the existing normal `gpu_print_stat -> shader_print_dtc_l1_stats -> cluster -> core -> LDST` boundary. OFF emits no AD rows. Debug-event quota is irrelevant. Snapshots are cumulative, never sum successive snapshots. Printing is const/read-only; snapshot CPU cost is separate from simulated timing.

Frame: `DTC_PROGRESSIVE_WAKE_V1_SNAPSHOT_BEGIN version=1 sms=... cycle=... no_event_cycle_sentinel=18446744073709551615`, then per-SM rows, then `DTC_PROGRESSIVE_WAKE_V1_SNAPSHOT_END version=1`. Missing frame with OFF means unavailable, not measured zero.

| Row / field | Definition / population |
|---|---|
| summary `broadcasts` | completed broadcasts, each physical allocation once |
| `first_notify_cycle_sum`, `last_notify_cycle_sum`, `span_sum` | sums across completed broadcasts, absolute first/last notification cycles and last-first; unfinished rows excluded |
| FANOUT `bin`, `count` | distribution of total notifications per completed physical allocation; bins 0..31 exact, bin32 means >=32; includes late merges, not post-end valid hits |
| LINE `physical`, `generation` | currently allocated pool slot/generation, bounded by configured physical pool; reclaimed generations are represented in aggregate counters, not historical LINE rows |
| LINE `data_ready`, `broadcast_done`, `notified`, `first_cycle`, `last_cycle`, `late_merges`, `refs` | current generation's actual data-stage state, broadcast state, total notified consumers, exact absolute first/most-recent notification cycles, within-broadcast late attachments, live Ref. First/last UINT64_MAX means no notification yet |
| `own_dep0_linewide_blocked_entry_cycles` | once per unique frontend service edge, count entries with >=1 held allocation, own pending=0, external=0, all data-ready, but any original broadcast-ready false. A counterfactual legacy gate observation, not GPU stall cycles or savings |
| `notified_frontend_ready_entries` | each live PIB entry counted at most once on a service-edge observation meeting the above new frontend predicate (without the legacy-block condition); frontend does not know LDST partial admission/fence ordering; valid-hit consumers with no required new notification satisfy this predicate vacuously |
| `notified_frontend_ready_entry_cycles` | sampled frontend-ready entry-cycles, including repeated observations while WB holds it |
| `late_merges` | distinct new Ref attachments while data_ready=true and broadcast_done=false; duplicate same-consumer/same-allocation accesses excluded; attachments before data-stage visibility excluded |
| LDST `admitted_notified_collectable` | first original ready observation for fully admitted CACHEABLE_LOAD consumers, own deps/external deps cleared. This is eligibility to enter the original collection machinery, not a collection grant; older same-warp fence may still block selection; valid-hit consumers are included without fabricating a new waiter notification |
| LDST `admitted_returns_to_retire_sum`, `retired` | sum of WB-retire cycle minus `admitted_returns_cycle`, count of successfully retired cacheable consumers. Sidecars excluded |

**Separate common boundary:** `service_entry.admitted_returns_cycle` is the first LDST service sample with all references admitted and every held allocation's real whole-line return accepted. It ignores own-waiter notification and external completion gating, and it clamps preexisting valid-hit data to this consumer's first qualifying observation. It is sampled before original ready observation in the same cycle. It does not make data readable or move any service edge. The retired-cohort sum from this boundary includes remaining notification/external/selection/collection/WB delay. Its definition can also be applied to an OFF observer, but this patch deliberately does not add OFF telemetry: the fixed X2 does not export this field. There is no measured OFF counterpart in this pack and no speedup inference.

Original `DTC_SERVICE_V1_fully_ready_to_complete_sum`, `ready_to_collect_sum`, `collection_cycles`, `wb_wait` keep their arithmetic identity and retired-consumer denominator. Their ready origin changes under ON from **all referenced broadcasts finished** to **this consumer's notified dependencies cleared and all allocation data available** (plus original external/admission conditions). Their ready-conditioned observations cannot be treated as the same readiness-conditioned population/timestamp as the old variant. Existing valid/pending hit fields continue to use broadcast-ready. New fields are versioned separately; do not compare old ready-to-complete averages as an equivalent time interval.

Storage/export are bounded: 33 histogram counters and 8 summary counters per OO frontend; five uint64 timestamps/counters and one data flag per physical slot, one observation flag per PIB entry; one timestamp per service entry and two counters per LDST. LINE export is <= physical_lines rows/SM, independent of run length. uint64 counters can overflow on sufficiently long runs; no unbounded event history is retained. At a drained terminal the pool may have zero LINE rows after reclaim; historical first/last times are sums over completed broadcasts, not a recoverable all-history per-generation trace.
